# 公開する前に、著者の手元で参加者の画面を動かす

**状態**: 提案（着手前）
**日付**: 2026-08-14
**前提**: [`docs/shared-app-principles.md`](../docs/shared-app-principles.md)（不変条件）、
[`plans/feat-shareable-collections.md`](./feat-shareable-collections.md)（D1–D10）、
[`plans/feat-shared-app-platform.md`](./feat-shared-app-platform.md)（宣言の表現力）、
[`plans/feat-shared-app-view-diagnostics.md`](./feat-shared-app-view-diagnostics.md)（壊れた事実を運ぶ経路）、
[`plans/feat-collection-pane-diagnostics.md`](./feat-collection-pane-diagnostics.md)（ペインで起きたことを貼れる塊にする）

この計画が答える問いは 1 つ:

> **ビューを書くのは LLM で、著者はそれを一度も動かさずに公開している。
> 動かす場所を、著者の Mac の中に作れないか。**

作れる。しかも作る場所は既にある — コレクションペインである。そしてそれが手に入ると、
**deploy と publish という 2 つの動詞は 1 つになる**。後半はその話である。

### 著者から見た形

著者が回すのはこのループで、動詞は 2 つしかない:

```
generate ──→ preview ──→ publish ──→ modify ──→ preview ──→ publish ──→ …
（ローカル）  （ローカル）  （Firestore）（ローカル）  （ローカル）  （Firestore）
```

`generate` と `modify` は LLM がリポジトリの中のファイルを書くこと、`preview` はそれを著者の Mac で
動かすこと。**Firestore に届くのは `publish` だけ**である。

これが引いている線は、共有アプリの中身が **2 種類ある**ということである:

| | 何 | どこにある |
|---|---|---|
| **コード** | `app.json`・コレクション宣言・ビューの HTML | publish までリポジトリの中だけ。git が持つ |
| **データ** | レコード（items） | **常に Firebase。ローカルには一度も存在しない** |

この線は既存のコードとそのまま一致する — `projectPublish` が射影するのは前者だけで、後者には
触らない。そして **preview はコードだけをローカルに持ち、データは本物を読む**。だから
「手元では全部見えた」も「フィクスチャが実データとずれる」も、どちらも起きようがない。
**フィクスチャは要らない**（下の 3）。**書き込み先も本物である**（下の 5）。

### 「ローカルだけ」には 1 つ例外がある — アプリの身元

厳密には **generate も Firestore に 1 つだけ書く**。preview がデータベースに触れる条件が
`apps/{aid}` の存在だからで、これは選択ではない: `firestore.rules` の `items` は read / create /
update / delete の**全部が `app(aid)` を引いて** owner と名簿を解決する。その文書が無ければ、
読みも書きも認可されない。

`appSlugs/{slug}` は**その条件ではない**。それが要るのは訪問者が名前で来るとき、つまり publish の
ときだけである。私たちが `identity` と一括りにしかけた 2 つは、寿命が違う:

| | いつ確定するか | 取り消せるか |
|---|---|---|
| `aid` ＋ `apps/{aid}`（owner） | **最初の preview の直前** | 取り消せないが、**誰とも競合しない**（aid は UUID、失敗しても孤児の文書が 1 つ残るだけ） |
| コード（宣言とビュー） | publish のたびに置き換わる | git が持つ |
| **`appSlugs/{slug}`** | **publish** | **取り消せない上に希少** |
| データ（レコード） | 常に Firebase | アプリ自身の経路で消す |

**取り消せない 3 つのうち、希少なのは slug だけである。** だから希少でない 2 つは generate 側に、
希少な 1 つは publish に置く。**preview は slug を要求しない**（原則 9。要求した瞬間に「試しに作る」が
名前を焼く）。

generate で slug も予約してしまう案は**採らない**。`appSlugs/{slug}` は published になるまで
「そのアプリの名簿の人」にしか読めないので（`firestore.rules` の `allow read`）、任意の名前が
空いているかは**取ってみるまで分からない**。`retireSlug` も名前を解放しない（`published: false` に
落とすだけで aid は残る）。つまり generate で予約すると、**捨てたアプリの数だけ名前が消える**。
払う代償は「全部作った後に `booking` が `booking-2` になっていると知る」ことだが、それは作り直しでは
なく URL が違うだけで、名前を焼く価格に見合わない。名前が本当に大事なアプリのためには、generate の
副作用ではなく**著者の一手としての明示的な予約操作**を別に置く。

## なぜ今これを書くか

[`feat-shared-app-view-diagnostics.md`](./feat-shared-app-view-diagnostics.md) は、
「壊れた事実が他人のブラウザから著者まで**戻ってくる**経路」を設計した。この計画は逆向きで、
**そもそも他人のブラウザに出す前に、著者が自分で踏む**ようにする。両方要る（後述）。

診断計画が挙げた実地の 3 件を、「プレビューがあったら捕まえられたか」で読み直すと:

| # | 起きたこと | プレビューで捕まるか | 捕まる理由 |
|---|---|---|---|
| 1 | `prompt()` がサンドボックスに無視される | **捕まる** | 同じ `sandbox="allow-scripts"`（`allow-modals` 無し）で描くから、著者の画面でも無視される |
| 2 | 申込みがポート上で捨てられていた | **捕まる（条件付き）** | 親が**同じ実装**であること。ボタンを押したのが著者なので、確認が出ないことは即座に分かる |
| 3 | `attendees` を数値で送っていた | **捕まる** | 拒否はフレームの外に出るので、ページが握り潰しても著者の目には残る |

条件付きの 1 件が、この計画で一番重要な設計判断である → **偽の親を作らない**（下の 1）。

## 設計の制約（先に固定しておく）

1. **プレビューは production の実行経路に入らない**（原則 1 / D7）。著者の Mac は公開後のアプリの
   実行経路にいてはいけない。プレビューは publish の**前**にしか存在しない機能で、公開されたページが
   ホストを見る経路を 1 本も作らない。
2. **プレビューは production より緩くない**。`allow-modals` も、CSP の緩和も、`connect-src` の穴も
   付けない。緩いプレビューは「手元では動いた」を量産する装置であり、無いより悪い。
3. **プレビューは権限を証明しない**（原則 2）。ルールはホストで走らない。プレビューが証明するのは
   **描画・配線・形**であって、**誰が何を書けるか**ではない。ここを曖昧にすると、原則 2 を
   「ホストの門番は診断である」と書いた紙の隣で、診断を保証として売ることになる。
4. **`__MC_VIEW` と `__MC_APP_VIEW` を同じペインに並べる**ことになる。前者はホスト契約
   （トークンを持って自分で取りに行く）、後者は共有アプリ契約（渡されたものを描く）。
   publish が `__MC_VIEW` を名指すビューを拒否するのはこの取り違えのためで、
   **プレビューが 2 つの契約を吸収するアダプタになったら、その拒否の意味が消える**。
5. **どのリポジトリの仕事か**を各項目に書く。今回は診断計画と逆で、**大半が MulmoTerminal 側**、
   次いで `@receptron/sharedapp` の抽出、mulmoserver は「持っていたものを渡して使う側に回る」だけである。

## 1. 偽の親を作らない — ランタイムを `@receptron/sharedapp` に出す（最優先）

診断計画の最後の教訓が、そのままこの計画の第 1 条になる:

> **偽の親は、本物の親と同じ入口で受けること。**

だから MulmoTerminal 側にブリッジを**書かない**。mulmoserver が持っている実物を共有パッケージに
出して、両方がそれを使う。移すもの:

| いま | 何をしている | 移す先 |
|---|---|---|
| `src/utils/publicViewSrcdoc.ts` | bootstrap 文字列・CSP・nonce | `@receptron/sharedapp/view`（純粋な文字列） |
| `src/composables/publicViewProtocol.ts` | `VIEW_MESSAGE` の語彙 | 同上 |
| `src/composables/publicViewMessage.ts` | 受信メッセージの読み取り・`ViewDataset` | 同上 |
| `src/composables/publicViewBridge.ts` | **いつ書くか**（確認・busy・nonce・port） | 同上（Vue 非依存、既にそうなっている） |
| `src/utils/viewChannel.ts` | `MessageChannel` と reactive 剥がし | 半分だけ。`toRaw` は Vue 依存なので、**unwrap を注入**にして DOM 側だけホストに残す |

残るのはホストごとの**外側の chrome** — 確認ダイアログの見た目、診断帯の置き場所 — で、
それはもともと `PublicViewFrame.vue` / `AppViewFrame.vue` にしかない部分である。

**この抽出は診断計画の 5 番と同じ抽出**であり、どちらを先にやってももう一方が安くなる。
先にこれをやる理由は、抽出しないまま MulmoTerminal に 2 本目のブリッジが生えると、
**#2 のような穴がホスト側にだけ塞がれた状態**が生まれ、プレビューが production より安全になる
（＝制約 2 の裏返しで、これも「手元では動いた」を作る）ためである。

mulmoserver 側は import 元が変わるだけで、既存のテストはそのまま通ること。通らなければ抽出の
線が間違っている。

## 2. 同じ入口・同じ制限で描く（MulmoTerminal）

プレビューの iframe は、公開ページと**バイト単位で同じ文書**を描く:

- `sandbox="allow-scripts"` — `allow-modals` も `allow-same-origin` も付けない
- `srcdoc` に `publicViewSrcdoc(html, nonce)`（CSP メタ・bootstrap・著者の HTML）
- レンダーごとの nonce、`ready` の照合、**ポートの受け渡し**、port 経由でのみ state を送る
- 書き込みは**親が描く確認**を通る（公開ビュー）／**通らない**（メンバービュー、
  [`plans/done/feat-shared-app-member-write.md`](./done/feat-shared-app-member-write.md)）—
  ここも本物と同じ非対称にする

**プレビュー専用の簡易経路を 1 本も作らない。** 「手元だから直接 `bridge.receive` を呼べばいい」は、
診断計画が名指した #2 の見逃しそのものである。

**そして親に渡す宣言は、本物でなければならない。** 制約 2 は「緩くしない」だが、**間違った診断を
返すプレビューは、緩いプレビューより悪い**。実際に踏んだ（2026-08-14）: 書き込みが未配線の間、
親に `{ submit: {} }` を渡していた。これは検査を止めるのではなく**全部を拒否**し、しかも
`unknown-collection` — 「あなたのページが送っている cid は宣言されていない」という意味の
コードで拒否する。宣言もページも正しかったのに、著者（LLM）は自分のリポジトリを 20 分デバッグし、
最後に「publish していないのが原因では」という誤った結論に達した。**プレビューが唯一の壊れた
ものだった。**

一般化: **プレビューが返すコードは、production が同じ入力に返すコードと同じでなければならない。**
「まだ配線していない」を表現してよいのは、production なら成功していたはずの地点だけである。
それより手前の判定を偽の入力で通してはいけない。

**そしてその地点に到達できなければならない。** 直した直後に 2 つ目を踏んだ（同日）: 宣言を
本物にしたら submit は通るようになったが、**確認を描いていなかった**ので `pending` に入ったまま
誰も accept も decline もできず、ページの promise は永久に settle しない。submit にタイムアウトは
無いので、画面には「確認の画面が出ます」が出たまま何も起きず、どこにも理由が出ない。

**これは「何もしないボタン」そのもの** — この機能が捕まえるために作られた失敗を、この機能が
作っていた。確認は production の親の契約の一部であって、あとで足す飾りではない。親が受けた
以上、必ず答えが返る経路が同時に要る。

## 3. データ — publish するはずのものを、書かずに計算する（MulmoTerminal）

公開ページが読むのは Firestore の射影であって、リポジトリのファイルではない。だから
プレビューが本物であるためには、**publish が書くはずのペイロードを計算して、書かずに使う**
のが唯一正しい入口になる:

```
app.json + コレクション宣言 + ビューの HTML
   → projectPublish（@receptron/sharedapp、publish が使うのと同じ関数）
   → config/public 相当 ＋ 各ビューの config ＋ HTML
   → 共有ランタイム（1 で出したもの）
   → iframe
```

- 射影を通すので、**`public.read` に載っていないコレクションはプレビューでも見えない**。
  「手元では全部見えた」が消える。
- レコードは**アプリの実レコード 1 択**である（著者は owner なので自分の資格情報で読める。
  読むだけで、production の経路には何も足さない）。宣言から生成したフィクスチャは**持たない** —
  データは常に Firebase であり、ローカルに 2 つ目の供給元を置いた瞬間に「手元では動いた」がまた
  作れるようになる。空のコレクションが空に描けることは、それ自体テストすべき状態である。
- mulmoserver のランタイムは既に `reader` / `writer` を**注入**で受けている
  （`readViewItems(aid, spec, reader)` / `performIntent(…, writer)`）。プレビューはここに
  ホスト側の実装を挿すだけで、判断のコードは 1 本のままになる。

## 4. 見る人を切り替える（MulmoTerminal）

参加者向けの画面は**誰が見るかで変わる**（`viewer.can` が変わる）。だからプレビューの第一級の
操作は「見る人の切り替え」である: 匿名 / サインイン済みの他人 / participant / 名簿のメンバー /
`assignee` である本人 / owner。

そして**ここに大きな注意書きが要る**（制約 3）。切り替えは**シミュレーション**で、
`can` を組み立てるのはホストのコードである — ルールではない。だから:

- プレビューは「**このロールならこう描かれる**」を証明する。
- プレビューは「**このロールならルールが通す**」を証明**しない**。
- 画面の文言もそう言うこと。「参加者として表示（権限は検証されません）」。

`can` の組み立てを 2 度書かないこと。共有ランタイムの `capabilitiesFor` を使い、入力
（宣言・名簿・見る人）だけをホストが与える。ここを独自に書くと、原則 11 が
「ロール名で分岐するのは、誰もレビューしない場所にルールをもう一度書くことだ」と言っている状態に
そのまま落ちる。

## 5. プレビューでの書き込みは、どこへ行くのか（MulmoTerminal）

押せないボタンはテストにならない。そして**書き込み先は実 Firestore である**。データは常に Firebase
だから、ここに例外を作ることは**書き込み経路にだけ偽の親を建てる**ことになる（上の 1）。スクラッチ層は
読みの合成としては作れるが、そのとき「書いたものが本当に書けたか」だけは誰も試していない状態になり、
それは診断計画が名指した #2（申込みがポート上で捨てられていた）と同じ形の見逃しである。

代わりに払うのは、**印と後始末**:

- preview からの書き込みには**印を付ける**。ただし **`created` されるレコードには付けられない** —
  ルールは公開の create を `hasOnly(createFields)` で読むので、余計なキーは注釈にならず**書き込み
  全体を拒否する**（実装時に判明。この計画の初版が「ホストが付けてホストが読む」と書いていたのは
  Firestore 上では実行不可能である）。データベースの中では著者の試し打ちと訪問者の申込みは**区別が
  つかない**。覚えていられるのはホスト側だけで、ペインが持つリストがその唯一の場所になる。
  だから「閉じたら消える」ことを画面で言い切ること — 消えるのはリストであって、レコードではない。
- 画面上で**実レコードと区別して描く**。どれが自分の試し打ちかは常に見えていること。
- **まとめて消す操作を持つ**。1 件ずつではなく「この preview で書いたものを全部」で消せること。

代償ははっきりしている: **消し忘れたら実データに残る。** それを受け入れるのは、消えないことより
「本番と違う経路で書けてしまうこと」の方が高くつくからで、この計画の第 1 条がそう言っている。

**副産物が 1 つあり、これが実は大きい。** 書き込みが本物の Firestore に行くということは、
**その書き込みはルールに judge される**ということである。preview は権限を証明しない（制約 3）が、
それは主に**読み**と**ロールの切り替え**の話で、著者が自分の資格情報で押したボタンについては、
ルールが本当に走る。つまり preview は「**owner として書いたときにルールが通すか**」だけは証明する。
他のロールについては証明しないし、**ルールが本番に deploy 済みかどうかも証明しない**（自分の
書き込みが通っても、それは今 deploy されているルールが通しただけである）。この 1 行以上を主張しない
こと。

**mirror を宣言したアプリは、batch でしか書けない。** ルールは 2 つ目の文書を `getAfter()` で読む
（`firestore.rules:425`「both writes are in one batch」）ので、単独の書き込みは拒否される — 安全な
方向にだが、著者に何も告げずに。`@mulmoclaude/core` の `FirestoreDocs` に batch は無く、**足さない**:
あの継ぎ目は core のストアがホスト非依存でいるためのもので、MulmoClaude は共有コレクションの
サポートを宣言していない（アクセサを外した）。仕える 2 つ目のホストがいない。MulmoTerminal は
`currentFirestore()` で生の Firestore を既に持っているので、**対の書き込みだけがそこを通る**。

なお `selfDelete` を持つアプリなら、後始末は**アプリ自身の取り下げ経路を踏む**のが最良である
（[`plans/feat-shared-app-self-delete.md`](./feat-shared-app-self-delete.md)）— 掃除がそのまま
1 本のテストになる。

**ホストが書き込みを拒否するときは、ルールの言葉ではなくホストの言葉で拒否する。**
`initialOk` 相当の判定をホストで書き直して「ルールと同じです」と言ってはいけない（原則 2）。
ホストが言えるのは宣言に照らした形の話（未宣言のフィールド、`transitions` に無い遷移、
必須欠け）までで、それは**診断**として十分に有用である。

## 6. フレームの外に、起きたことを必ず出す（MulmoTerminal ＋ 診断計画と共有）

プレビューの価値の半分は、**ページが自分の成功について嘘を描けない**ことにある。だから親は
iframe の外に、要求・答え・拒否理由・無視された呼び出し（`alert` / `confirm` / `prompt`）・
未捕捉エラーを出す。これは診断計画の 2 と 3 の**同じ実装**であり、プレビューで先に作って
production に出すのが安い順序になる（読者が著者 1 人なので、個人情報の許可リストの検証も
ここでなら安全にできる）。

## 7. LLM が回せる形にする（MulmoTerminal）

人間が押すプレビューだけでは、診断計画が名指した「**LLM は一度も動かしていない**」は半分しか
消えない。同じ親・同じ srcdoc を**ヘッドレスで**駆動する口を作る:

- `manageSharedApp` に `action: "preview"` — ビュー id と見る人を受け取り、ページを読み込み、
  宣言されたシナリオ（このボタンを押す → submit がこの cid に来る → 答えが表示される）を回し、
  **診断バッファをテキストで返す**。
- 走らせるのは**実ブラウザ**（`puppeteer` は既に依存にある）。診断計画が P1 で言った通り、
  jsdom は `srcdoc` のサンドボックスも `allow-modals` の不在も `MessagePort` の寿命も持たない —
  つまり #1 と #2 の**どちらも再現しない**。ロジックの反復に jsdom を使うのは構わないが、
  境界の契約テストは実ブラウザ 1 本を必ず持つ。
- これができた時点で、**LLM は自分の書いたページに対してテストを書ける**。以降の同種の不具合は
  publish 前に落ちる。

## プレビューが証明しないもの（ここを曖昧にしないこと）

| 証明する | 証明しない |
|---|---|
| ページが描けること・配線が通っていること | **見る人を切り替えたときルールが通すこと**（切り替えはホストのシミュレーションで、ルールは走らない、原則 2） |
| 射影に載っているデータだけで描けていること | 他人の資格情報での読み取り |
| サンドボックスと CSP の下で動くこと | 他人の端末・他人のブラウザ・モバイル |
| 宣言に照らした形の誤り | **同時実行**（先着枠、id の衝突、原則 3 / 4） |
| 著者が **owner として書いたときにルールが通すこと**（書き込みは実 Firestore に行くため） | 他のロールで書いたときにルールが通すこと |
| 1 人の操作の流れ | 2 人目・3 人目の存在するアプリ |
| — | **ルールが本番に deploy 済みかどうか**（mulmoserver に CI は無く、状態はどこにも記録されない） |

最後の 1 行が特に効く。新しい語彙を使う宣言は、ルールが出ていなければ本番で fail closed になる。
プレビューは全部緑にして、訪問者が壊れたページを見る。**プレビューは、その種類の失敗を隠す**。

**任意の追加段（あとで）**: Firestore エミュレータを実 `firestore.rules` で走らせられれば、
上の 1 行目と最終行は消える。ただし Java が要り、ルールのテキストは mulmoserver のもので、
共有アプリの利用者の Mac に置くものではない。**既定にしない。** 置くなら
`@receptron/sharedapp` がルールをバージョン付きのデータとして同梱し、あるときだけ使う段にする。

## deploy と publish を 1 つにする

> **「手元で完全にテストできるなら、deploy と publish を分ける必要は無いのでは」**

無い。**動詞は `publish` 1 つになる。** ただし理由の半分は「テストできるようになったから」ではなく、
**分割の根拠だと思われていたものが、そもそも根拠ではなかった**ことにある。

### 分割の根拠だと思われていたもの

「聴衆が 2 つある — 名簿と世界 — だから動詞も 2 つ」という説明は成り立たない。`publish` は
**すでに名簿だけのアプリを扱えている**（`PublishSuccess.publicOpen` の JSDoc: `public` ブロックの
無い宣言は「名簿の URL にスキーマを publish する」と書いてある。`false` は失敗ではなく正常な結末で
ある）。つまり**聴衆を決めているのは宣言であって、叩いた動詞ではない**。動詞を 1 つにしても表現力は
1 ミリも減らず、むしろ聴衆が操作の属性からアプリの属性に戻る。

### staging がしていた 6 つの仕事

| | staging の仕事 | 1 動詞にしたらどこへ行くか |
|---|---|---|
| S1 | 名簿の人が本物の Firestore で試す場 | **消える。** preview がその場になる（描画・配線・形について） |
| S2 | ルールと認証の実地確認 | **どこにも行かない。** preview は権限を証明しない（制約 3） |
| S3 | live なアプリの版の入れ替えを訪問者に見せない | **publish の内側に残る。** テストではない |
| S4 | fail closed の順序 — 途中で落ちても公開が付かない（原則 8） | 同上 |
| S5 | 半端な deploy の検出（`deployId` の組、チェックリスト 7） | 同上。1 回の操作の中に畳む |
| S6 | 2 人目以降・同時実行 | どこにも行かない（公開後にしか出ない） |

**消えるのは動詞と段であって、書き込みの二段ではない。** `staging/{cid}` という Firestore の
コレクションは残り、`publish` が stage → 組の検査 → 昇格 を 1 回の操作の中で行う。揃わなければ
何も昇格させない。

`deploy` が今ほんとうに独占している仕事は 3 つあり、いずれも publish の内側に入る:

1. `apps/{aid}` の初回作成と `appSlugs` の予約（他の書き込みの認可がこれに依存する — 「app
   document first」）
2. `staging/{cid}` への書き込み
3. `projectDeploy`（`projectPublish` とは未知キーの扱いが非対称。**preview も publish も
   `projectPublish` を使う**ので、この非対称は消える側に落ちる）

### `/staging/{aid}` は要らない

このルートは「publish の前に名簿の人が試す入口」としてしか存在していない —
`server/infra/shared-app-tool.ts`、`slug.ts`、`appViews.ts`、`staged.ts`、スキル、ChangeLog の
全部がそう説明している。preview がその仕事を取るので、**入口ごと消える**。名簿の人の恒久的な入口は
`/m/{slug}` であって staging ではない
（[`plans/done/feat-shared-app-member-view.md`](./done/feat-shared-app-member-view.md)）。

これは前の整理（「staging は公開前の試用入口という**説明をやめる**だけで、入口は残す」）からの
**変更**である。説明をやめても入口が残れば、著者も LLM も「まず staging を見に行く」を再発明する。

**撤去は 1 対 1 で畳める。** staging の 3 本は `/m/` の 3 本にそのまま対応し、失われる能力は無い:

```
staging/:aid           → m/:slug              (StagedApp        → MemberApp)
staging/:aid/view/:id  → m/:slug/:id          (StagedAppView    → MemberApp)
staging/:aid/:cid      → m/:slug/records/:cid (StagedCollection → MemberCollection)
```

残る入口は 3 つで、**2 つではない**（`../mulmoserver/src/router/index.ts`）:

| 入口 | 誰の顔 | 読む場所 | ルール |
|---|---|---|---|
| `a/:slug` | 匿名の訪問者 | `apps/{aid}/config/*` | `allow read: if true` |
| `m/:slug` ＋ `m/:slug/:id` ＋ `m/:slug/records/:cid` | 名簿の人（スタッフ） | `apps/{aid}/member/*` | `staffOf` |
| `p/:slug` ＋ `p/:slug/:id` | participant（申し込んだ本人） | `apps/{aid}/roster/*` | `listedIn` |

`/p/` を「`/a/` のサインイン分岐」にできない理由は表の右 2 列にある。公開ページの config は
`allow read: if true` なので、participant 向けのデータをそこに置けば世界が読む。そして
`appViews.ts` が言う通り、**一つの射影は両方に仕えられない** — スタッフのデータセットを渡された
participant のページは「描画が減るのではなく、ルールに拒否されて**失敗する**」。roster tier の
ページを著者が宣言しなければ tier ごと消えるので、公開フォームだけのアプリに `/p/` は現れない。

**代償が 1 つある: `slug` が必須になる。** 今は「`/staging/{aid}` だけで到達できるアプリは slug を
要らない」（`deploy.ts` の JSDoc）。入口を消すと、名簿を持つアプリは名前を持たなければ誰も辿り
着けない。**名簿だけのアプリも publish を叩く**ことになるが、動詞が 1 つになった以上これは矛盾では
なく設計通りである。そして preview は依然として slug を要求しない — 名前が要るのは publish の
時点であって、preview はそれより前に立っている（上の「アプリの身元」）。

（ルートの削除は mulmoserver 側の仕事。MulmoTerminal 側で変わるのは文言と、`slug.ts` の任意性である。）

### サインインの後にどこへ行くか

入口が 3 つあるので、`/a/{slug}` でサインインが起きたときの行き先を決めておく。**条件はロールでは
なく「なぜサインインしたか」**である — ロールで分けると、これから申し込む他人（まだ名簿にいない）を
拒否されるページに送ることになる。

| サインインの起点 | 直後の行き先 |
|---|---|
| **送信するため**（送信ボタンがサインインを要求した） | **`/a/` に留まる。** 書きかけを持ったまま送信を完了し、完了後に「自分の予約を見る →」を出す |
| **戻るため**（ヘッダーの「サインイン」、「もう予約している方はこちら」） | **`/p/{slug}` へ。** ただしその人が roster tier のページを実際に持つときだけ。無ければ留まる |
| 既にサインイン済みで `/a/{slug}` に来た | **遷移しない。** 公開の顔を見せ、`/p/` は差し出すだけ |

staff / owner も同じで、`/m/{slug}` は差し出すだけである（オーナーが公開リンクを開くのは、たいてい
公開の顔を確かめるためである）。

この規則が守っているもの: 記入中のものを失わない（現行の `staysOnSignIn: true` の存在理由が、
そのまま左半分になる）。持ち物の無いページに人を送らない。そして **`/a/` の保証が条件にならない** —
変わるのはサインイン**イベント後の遷移**だけで、ページの中身は今まで通り無条件にサインアウトで
描け、内部語彙を 1 つも持たない。持ち物の有無は roster tier の config が読めるかで判定するので、
読めなければ持ち物なし、という fail closed がそのまま条件になる。

（mulmoserver 側。preview / publish の一本化とも staging 撤去とも独立に進められる。）

### 提案する形

1. **`publish` が working tree から直接行う。** stage → 組の検査（`deployId`）→ 昇格 を 1 回の操作の
   中で行い、揃わなければ**何も昇格させない**。
   今のスキルにある注意書き — 「**`publish` は deploy されたものを昇格する**。編集したなら先に
   deploy し直せ。さもないと誰も見ていない版を公開する」— は消える。これが今回いちばん大きい
   「概念の削除」で、削るのは段ではなく**順番を人間に覚えさせること**である。
2. **`deploy` は落とす。** エイリアスとしても残さない。残せば、それが何をするのかを説明する文が
   永久に要る。
3. **書き込みの順序は 1 文字も変えない。** `apps/{aid}.public` は最後（原則 8）。再 publish が
   「開いたまま版が混ざる」を選んでいることも変えない。
4. **`confirm` の文面は宣言から決める。** D10 の非対称は「動詞の違い」ではなく「聴衆の違い」だった
   ので、`public` ブロックを持つアプリの publish は**世界に渡す言葉**で確認し、持たないアプリは
   名簿の言葉で確認する。一律に緩い方へ寄せると移行ゲートの意味が消え、一律にきつい方へ寄せると
   名簿だけのアプリを更新するたびに「世界に公開しますか」と聞くことになり、確認が摩耗して同じ場所に
   落ちる。
5. **UI の言葉**: 「プレビュー」と「公開する」。「deploy」「staging」は失敗の説明の中にだけ残る。

### 変わらないこと

- 取り消せない 3 つ（`aid` / `appSlugs` の予約 / `apps/{aid}`）は変わらない。**1 動詞にすると
  「試しに公開」が名前を取る**ので、slug の予約はこれまで以上に重い。上に書いた通り、
  **preview は slug を要求しない**。
- `staging/{cid}` の書き込みも、`deployId` の組も、fail closed の順序もそのまま。消えたのは
  それを**人間が別の動詞として叩くこと**である。

### 取り下げは、クライアントにレコードを選ばせない

undo は**著者の Firestore ハンドル**で走る。著者は自分のアプリの何でも消せるので、
ルートが cid と id を受け取る形にすると、それは**呼び出した誰かが選んだ** cid と id になる —
他人の本物の予約を消して、それが押さえていた枠を `open` に戻せて、しかも書き込みは
完全に authorized。ルールは何も止めない。

なので undo が受け取るのは、書き込んだ**その瞬間にサーバが自分で発行したトークン**だけ。
レコードも、どのアプリのものかも、サーバ側の対応表が持つ。画面に出る cid / id は
著者が読むためのもので、操作の対象ではない。

対応表はプロセス内の `Map`。寿命は画面の一覧と同じで、どちらも保存されない —
セッションが終われば、プレビューが書いたものはただのレコードになる。成功した時点で
エントリは消す（1 トークン 1 回）。失敗した時は残す — レコードはまだそこにあるので、
やり直せなければならない。

### 生成フォームは「ページが無いアプリ」ではない

アンケート・申し込み・「参加します」の 1 ボタン — `public.submit` だけを宣言してビューを持たない
アプリは、公開サイトでは**宣言から組み立てたフォーム**が出る。ページが無いのではなく、
著者が書いていないだけで、他人はそれに出会う。

プレビューが描くのは**その射影**であって、フィールド名から組み直したものではない。どの欄が
あるか・並び・ラベル・必須・型・そして書かれるレコードは、すべて `config/public` と、公開側の
送信経路が呼ぶのと同じ `writableFields` が決める。ペイン自身のものは**マークアップだけ**で、
だから公開サイトの見た目とは違う。サンドボックスにも入れない — ここには囲うべき著者のコードが
無い（フォームは導出であって、書かれたものではない）。

宛先の欄は出さない。ルールは `request.auth.token.email` と比べるので、入力欄は間違える方法しか
提供しない。ステータスも同じ理由で `initialStatus` に固定される。

**P4 は P2 と P5 の後**にしか置けない。プレビューが無いうちに「publish は working tree から」に
すると、誰も見ていない版が世界に出る経路を作るだけになる。**P4b は P4 の後** — 動詞が 1 つになる前に
入口を消すと、deploy したものを見に行く場所が無くなる。

- **プレビュー専用の軽い契約**（トークンを渡す、`allow-modals` を付ける、CSP を緩める、

  書き込み経路にだけ偽の親を建てないこと（上の 5）。
- **`__MC_VIEW` と `__MC_APP_VIEW` の両対応アダプタ。** publish の拒否が意味を失う（制約 4）。
- **宣言から生成したフィクスチャでプレビューする。** データは常に Firebase であり、ローカルに
  2 つ目の供給元を置けば「手元では動いた」がまた作れる（上の 3）。
- **動詞を 2 つのまま残す。** 「聴衆が 2 つあるから動詞も 2 つ」は成り立たない — `publish` は
  すでに `public` ブロックの無いアプリを正常系として扱っており、聴衆を決めているのは宣言である。
- **`deploy` をエイリアスとして残す。** 何をするのかを説明する文が永久に要る。
- **二段の書き込みまで消す。** S3・S4・S5 はテストではない（上の表）。消せるのは**人間に順番を
  覚えさせること**であって、`staging/{cid}` → 検査 → 昇格 ではない。
- **`/staging/{aid}` を「名簿の恒久的な入口」として残す。** 名簿の入口は `/m/{slug}`。残すと
  「まず staging を見に行く」が再発明される。
- **generate で slug も予約する。** 空きは取ってみるまで分からず、`retireSlug` も名前を解放しない
  ので、捨てたアプリの数だけ名前が焼ける（上の「アプリの身元」）。
- **`/p/{slug}` を `/a/{slug}` のサインイン分岐にする。** 公開ページの config は
  `allow read: if true`。一つの射影は両方に仕えられず、participant のページはルールに拒否されて
  失敗する。
- **サインイン後に無条件で `/p/` へリダイレクトする。** `/a/` でサインインする人の大半はこれから
  申し込む他人で、持ち物のないページに着く。しかも記入中のフォームを失う。
- **プレビューが通ったら公開してよい、と言う。** 言えるのは「描画と配線は通った」まで。
  ルールの deploy 状態を含め、プレビューが隠す失敗が 4 種類ある。
- **エミュレータを既定にする。** Java と、他人の Mac に置くべきでないルールのテキストが要る。

## 新しい能力を足すときに、先に答えること（原則の末尾のチェックリストへの答え）

1. **強制はどこにあるか。** どこにも増えない。プレビューは**診断だけ**を足す。1 行も権限を判断
   しないことが、この機能の正しさの条件である。書き込みが実 Firestore に行くので**そこはルールが
   強制する**が、それは既存の強制であって、この機能が足したものではない。
2. **どの経路の式数が増えるか。** ルールは変わらない。0 式。
3. **ルールの deploy が先か。** 関係しない。ただし**プレビューはルールの deploy 状態を隠す**ので、
   publish の出力がそれを言い続けること。
4. **`projectDeploy` と `projectPublish` は非対称。** プレビューは **`projectPublish` を使う**。
   deploy の射影で描くと、未知キーの扱いが違うぶん本番と別のものが描ける。P4 で `deploy` を落とす
   時点で `projectDeploy` は呼ばれなくなるので、この非対称そのものが消える。
5. **live なレコードがあるとき宣言を変えられるか。** 変わらない。ただしプレビューは
   **移行ゲート（`records.ts`）を回す場所**として最良で、publish で初めて知るのをやめられる。
6. **staged な設定と現在の名簿の組。** P4 で 1 動詞にする際、`scopedFields.ts` の "WHY TWICE" が
   要求する 2 回目の検査を**畳んで消さない**こと。1 回の操作になっても検査は 2 回である。
7. **半端に終わった deploy を publish は見分けられるか。** 1 動詞にすると、この検査は操作の
   **内部**に移る（S5）。`deployId` の組が揃わなければ昇格させない、を中で守ること。
8. **否定と同じ数の肯定のテスト。** プレビューの契約テストは「拒否が出る」と同じ数だけ
   「本物と同じに描ける」を持つこと。
