# 公開ビューが壊れたとき、それが書いた者に届くようにする

**状態**: 2 は実装済み（2026-08-15）。1・3・4 は提案のまま、5 は別計画で実装済み、6 は継続
**日付**: 2026-08-14
**前提**: [`docs/shared-app-principles.md`](../docs/shared-app-principles.md)、
[`plans/feat-shared-app-platform.md`](./feat-shared-app-platform.md)（D1–D10）

この計画が答える問いは 1 つ:

> **ビューの HTML を書くのは LLM で、それが動くのは他人のブラウザの中である。
> 壊れたとき、その事実はどうやって書いた者まで戻ってくるのか。**

現状の答えは「戻ってこない」。人間が症状を言葉にして運ぶ以外に経路が無く、
しかも運べる言葉が「止まっているみたい」しか無い場合がある。

---

## なぜ今これを書くか — 実地で出た 3 件

2026-08-13〜14 に会議室予約アプリを 1 つ作る間に、ビュー由来の不具合が 3 件出た。
**壊れ方の種類が 3 つとも違う**ことが、この計画の骨格になっている。

| # | 起きたこと | ページに出た手掛かり | 書いた者に届いたもの |
|---|---|---|---|
| 1 | `prompt()` がサンドボックスに無視される | コンソール 1 行（例外は出ない） | ユーザーが貼った 1 行 |
| 2 | 申込みがポート上で捨てられていた（mulmoserver #184） | **何も無い**（Promise が永久に未解決） | 「止まっているみたい」 |
| 3 | `attendees` を数値で送っていた | `not-a-submission` という返答 | ページが握り潰し「取られました」と表示 |

分類すると:

- **答えが来ない**（#2）— 観測点がそもそも存在しない。最悪。
- **失敗が例外の形をしていない**（#1）— 例外ハンドラをいくら足しても捕まらない。
- **答えを捨てている**（#3）— 情報はあったのに、ページと返答の粒度が悪くて消えた。

3 件とも **LLM 自身は一度もそのページを動かしていない**。これが背景条件で、
以下のどれも「LLM が動かせるようにする」か「動かなくても事実が届く」かのどちらかを狙う。

---

## 設計の制約（先に固定しておく）

1. **著者の Mac を実行経路に置かない**（D7）。診断のために常時接続を要求してはいけない。
2. **ビューの HTML は信頼されていない**。壊れているページに自分の状態を報告させるなら、
   出力先は**フレームの外**でなければならない。中に描かせると、壊れた者の自己申告になる。
3. **injected ブートストラップは我々のコード**（`../mulmoserver/src/utils/publicViewSrcdoc.ts`）。
   フレームの中で唯一信用できる足場はここだけで、以下の多くはここに載る。
4. **見知らぬ人のブラウザに新しい書き込み経路を増やさない**。診断を Firestore に書く案を
   採らない理由（下の「採らなかったもの」）。
5. **どのリポジトリの仕事か**を各項目に明記する。大半は mulmoserver 側で、
   MulmoTerminal 側は publish 時の門番とスキルの文言だけである。

## 1. すべての要求に締切を持たせる（最優先・mulmoserver）

`request()` が配る Promise に期限を入れ、答えが来なければ
`{ ok: false, error: "no-answer", kind, cid }` で**解決する**（reject ではなく）。

- #2 は**これだけでページ自身が名指しできた**。「止まっている」は人間の印象だが、
  「submit(bookings) に N 秒答えが無い」は事実で、そのまま貼れる。
- 無応答を「起こらないこと」として設計するのをやめる、という一点。分散システムで
  タイムアウトの無い要求を書かないのと同じ理屈が、iframe の境界にも要る。
- **注意**: 親は人間の確認を待つ。素朴な締切だと「確認を読んでいる人」を無応答と呼ぶ。
  → 親が「受け取った」を即返す 2 段階（ack → result）にする。**ack には短い締切**。
  #2 は ack が来ない形でここに捕まる。

  **結果の側を締切なしにしてはいけない**（レビュー指摘、P1）。ack は「届いた」しか証明せず、
  その後に確認ハンドラが例外を投げる・結果メッセージが落ちる・親が壊れる、のどれでも
  Promise は再び永久に未解決になる — つまり #2 と同じ穴が後半に残る。要求の状態を
  **観測できる形**にするのが答え:

  | 段階 | 締切 | 破れたときに言えること |
  |---|---|---|
  | 送信 → ack | 短い（秒） | 「親に届いていない」 |
  | ack → **人が確認中** | 無し。ただし親が生存の合図を刻む | 合図が途切れれば「親が落ちた」 |
  | 人が答えた → result | 短い（秒） | 「答えたのに結果が返らない」 |

  肝は、**人間を待っている状態を「無応答」と同じ名前で呼ばない**こと。両者を区別できれば、
  結果側にも締切を置けるようになる。

## 2. 「黙って無視される」を声にする（mulmoserver）

サンドボックスの制約は**事前に分かっている**。ブートストラップが `alert` / `confirm` / `prompt`
を自前の実装で置き換え、呼ばれた事実を記録する（返り値は今と同じく無効のまま）。
併せて `window.onerror` と `unhandledrejection` を拾う。今はどちらもフレームの中で死んでいる。

- #1 はコンソールを見ていた人間が居たから届いた。見ていなければ届かなかった。
- 拾ったものは**フレームの外へ**（制約 2）。親が小さな帯を出す:
  「このページはブラウザが無視する呼び出しを 1 件行いました」。
- publish 時の拒否（`modalCallIn`）と**二重にやる価値がある**。静的検査は既知の書き方しか
  捕まえられず、実行時のこれは書き方を問わない。

**実装した（2026-08-15、`@receptron/sharedapp` 0.6.0）。** ブートストラップが未捕捉の例外・
未処理の rejection・差し替えた `alert`/`confirm`/`prompt` を拾い、`mc-public-view:notice` として
親に送る。設計で 1 つ変えたのは経路で、**ポートではなく window に送る**: 一番効くのは `ready()`
より前（解析中に script が投げたページは ready を呼ばない）なので、ポートを待つ notice は
「一番必要な場合にだけ消える」ものになる。nonce は `ready` と同じ根拠。

受け口 `BridgePorts.notice` は**任意**で、既定の「捨てる」が正しい: 他人のブラウザには人が読む
場所が無い。最初の利用者は著者自身のプレビュー（[ペインの診断](./feat-collection-pane-diagnostics.md)
の P7）で、そこでは読者が著者本人なので `detail`（ページが書いた文字列）を捨てずに残し、
出所を明記する。上の 3 の表が「例外の本文は捨てる」としているのは**公開側の話**で、この区別は
そのまま残っている。`code` の側は両方で固定 enum に正規化する。

## 3. 人間が 1 回で運べる塊にする（mulmoserver）

1 と 2 で事実は集まるが、それは他人のスマホの中にある。著者の Mac は実行経路に居ない（制約 1）
ので、**運ぶのは人間**である。ならば運びやすくする。

- 直近 N 件のリングバッファ（要求・答え・拒否理由・無視された呼び出し・未捕捉エラー）。
- コピーボタン 1 つ。ユーザーは貼るだけ、LLM は憶測なしで読める。
- **個人情報を入れない — 意図ではなく、schema で強制する**（レビュー指摘、P1）。
  「値ではなくキー名を持つ」だけでは足りない。`window.onerror` のメッセージと
  `unhandledrejection` の理由は**信頼していないビューが作った任意の文字列**で、
  `throw new Error(email)` と書けば個人情報がそのまま入る。しかもこのバッファは
  コピーボタンで他人や LLM に渡ることが前提なので、素通しは事故になる。

  したがって記録できるものを**許可リストで定義する**:

  | 入れてよい | 入れてはいけない |
  |---|---|
  | ホストが作ったコード（`no-ack` / `undeclared-field` / `modal-ignored`） | 例外のメッセージと stack |
  | 宣言に載っているフィールド**名** | フィールドの値 |
  | 経過ミリ秒 | 拒否理由に埋め込まれた任意文字列 |
  | 要求の種類と cid — **ただし下記の正規化を通したもの** | ビューが送ってきたままの文字列 |

  **要求の種類と cid はビューが送ってくる**（レビュー指摘、P1）。`request()` を呼ぶのは
  信頼していないページなので、`kind` も `cid` もそのままでは任意長の任意文字列である。
  許可リストを謳いながらここから素通しすれば、**コピーされる面に好きな文章を書き込める**
  経路が残る（診断の汚染であり、読むのが LLM なら注入でもある）。

  受け側が**固定の enum とだけ突き合わせる**こと。`submit` / `transition` / `assign` /
  `withdraw` のどれでもなければ `unknown-kind` というホスト側のコードに落とす。`cid` は
  同じく**射影に載っている cid の一覧**と突き合わせ、無ければ `unknown-collection` にする。
  記録に入るのは常にホスト側の語彙であって、ページから来た文字列ではない。

  例外は「起きた事実と、起きた場所（あれば script の行）」だけを記録する。**本文は捨てる。**
  デバッグしにくくなるのは承知の上で、コピーされる前提の面に任意文字列を載せない方を採る。

## 4. 返答そのものを名指すものにする（mulmoserver）

`not-a-submission` は、**親がどのキーで落ちたか知っているのに**捨てている返答である。
「`attendees` が数値だった」と返せば、ページが握り潰しても人間の目には残る。

- 同様に、締切超過・未サインイン・必須欠けを区別して返す（一部は既に区別されている）。
- **ページが中継できるのは、渡されたものだけ**。ここを直さない限り、テンプレートに
  「`result.error` を出せ」と書いても中身が空である。

## 5. publish 前に LLM が走らせられる場（mulmoterminal + mulmoserver）

ここが「LLM もデバッグできない」への本丸。今の LLM は HTML を書いて publish するだけで、
一度も動かしていない。

- ブートストラップ＋**偽の親**を Node 側に置き、ビューを読み込み、状態を流し込み、
  ボタンを押し、「submit が要求されたか」「答えを表示したか」を確かめる。
- **jsdom だけにしてはいけない**（レビュー指摘、P1）。jsdom はビューのロジックは動かせるが、
  `srcdoc` のサンドボックスも `allow-modals` の欠如も `MessagePort` の寿命も実装していない —
  つまり #1 と #2 は**どちらも jsdom では再現しない**。これを唯一の走者にすると、この文書の
  最後にある教訓（本物と違う入り口から入るテスト）をそのまま繰り返す。
  → **2 段構え**にする: ページのロジックは jsdom で速く回し、境界そのもの
  （サンドボックスがモーダルを食うこと、ポートの受け渡しと解放）は**実ブラウザ 1 本**の
  契約テストで押さえる。後者は数が要らない代わりに、絶対に省いてはいけない。
- **LLM が自分の書いたページに対してテストを書ける**のが決定的な差で、以降の不具合は
  publish 前に落ちる。
- ブートストラップは mulmoserver にあるので、**共有する形**を決める必要がある
  （`@receptron/sharedapp` に出すのが素直 — 既に射影のコンパイラがそこに居る）。

## 6. 既知の壊れ方は publish で拒否する（mulmoterminal・着手済み）

`modalCallIn` がこれ（#1697）。**安いが既知の種類しか捕まえられない**ので、1〜5 の代わりには
ならない。新しい種類が見つかるたびに増やす場所、という位置づけが正しい。

- レビューで判明した通り、HTML を正規表現で走査する検査は**両方向に外す**:
  文字列中の `//` で本物を見逃し、`<p>alert() は使えません</p>` で無実を拒否する。
  文字列とコメントを区別しながら見る小さな走査に替えた（#1697）。
- **走る場所は 3 つある**: `<script>`、`on*` ハンドラ、`javascript:` の URL。1 つでも
  見落とすと、同じ silent failure がその形で通る。

## 順番

**1 → 2 → 3** で「症状が伝わらない」はほぼ消える。4 は 3 と同時にやると効果が倍になる
（運ぶ塊の中身が名指しになる）。5 は投資が大きいが、**LLM が検証できる**唯一の道なので、
1〜4 が落ち着いたら着手する。6 は継続。

すべて mulmoserver 側が先で、MulmoTerminal は最後にスキルの文言を合わせるだけになる。

## 採らなかったもの

- **診断を Firestore に書く。** 見知らぬ人のブラウザに書き込み経路を増やすことになり、
  ルールの手当ても、濫用の面倒も増える。人間が運ぶ方が今の設計に合っている（制約 1・4）。
- **著者のホストにログを送る。** D7 に反する。著者の Mac が寝ていても動くことが共有アプリの
  前提で、診断のためにそれを崩すのは本末転倒。
- **`allow-modals` を付ける。** #1 は消えるが、他人のブラウザで著者の HTML がモーダルを
  出せるようになる。今の「フレームは無力」という設計を、症状 1 件のために崩す価値はない。
- **ビューの HTML を禁じて宣言だけにする。** 原則 11 の逆。表現力の問題は表現力で解く。

## 今回いちばん高くついた教訓（この計画の外だが、忘れないために）

#2 を既存テストが**全部**見逃したのは、テストが本物の通る継ぎ目を通っていなかったから
である（すべて `bridge.receive` を直接呼んでいて、実物が使うポートを一度も通らなかった）。

観測性をいくら足しても、テストが実物と違う入り口から入っていれば同じことが起きる。
5 を作るときの最初の設計基準はこれ — **偽の親は、本物の親と同じ入り口で受けること**。
