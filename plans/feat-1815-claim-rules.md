# パスの排他が決めること（#1815 PR1c）

現象 A（複数セッションが同じところを直し続ける）への答えは claim レジストリで、
設計は取得の形を4つ挙げている:

1. 正規化した識別子（実パスに解決し、大文字小文字とシンボリックリンクを畳む）
2. compare-and-set で取り、取れなかった側は待つ
3. 期限つきにして、期限内は所有者が延長する
4. 所有者トークンを持たせ、期限切れの旧所有者の書き戻しを世代で拒否する

この PR は **1・3・4 の「判断」部分**を純関数で置く。2（ファイルシステム上の CAS）は次の PR。

## なぜ分けるか

PR1b が示したとおり、I/O のレビューは判断のレビューを埋もれさせる。
そして間違いが**見えない**のは判断のほうである — セグメント境界を見ない prefix 判定は
`src/foo` と `src/foobar` を同じ排他にしてしまい、テストも本番も静かに通る。

## 正規化も包含判定も再発明しない

**包含判定は `server/infra/path-within.ts` の `isWithin`。** 最初これを手書きしたが、
あのモジュールの冒頭に「この比較は8箇所で手書きされ、うち2箇所が Windows で壊れていた」と
書いてある。9箇所目を書いていた。`isWithin` は platform を引数に取り、win32 では
大文字小文字を畳み、末尾セパレータと root を `path.resolve` で処理する。
手書きの版はそのどれも持っておらず、さらに自前の末尾セパレータ刈りで
正規表現のバックトラッキングとスタック枯渇を順に踏んだ。

**正規化は `server/infra/canonical-path.ts`。** realpath でシンボリックリンクを解決する。
このモジュールは正規化済み・絶対パスを受け取る前提で書く。
2つ目の正規化器は2つ目の答えであり、「同じパスか」に答えが2つあることこそ排他が耐えられないもの。

### 残る穴（キーを作る側の仕事）

`canonicalPath` は**まだ存在しないセグメントを typed のまま再付加する**。
claim は作業の前に宣言されるので、これから作るファイルへのパスは普通の場合である。
大文字小文字を区別しないボリュームでは `…/NewThing.ts` と `…/newthing.ts` が
1つのファイルに対する2つのキーになり、2つのタスクが両方 claim できる。

`isWithin` は Windows では畳むのでそこは閉じている。macOS は意図的に畳まない
（`path-within.ts` の理由: case-sensitive APFS は対応構成であり、
包含ガードで当て推量に畳むと通る範囲が広がる）。
**存在しないセグメントをボリュームの実際の挙動に合わせてキー化するのは registry の仕事**で、
この層では決められない。隠さず書いておく。

## 決めること

| | |
|---|---|
| `covers` | 一方が他方を含むか。**`isWithin` に委譲**（セグメント境界、Windows では case 畳み込み） |
| `pathsConflict` | どちらが含んでも衝突。対称 |
| `conflictingPaths` | 欲しい集合のうち、保持中と衝突するもの |
| `isLive` | 期限は**排他的**。`expiresAt` ちょうどで終わり |
| `blockingClaims` | 生きていて重なるものだけが邪魔。期限切れは邪魔ではないが、消えてもいない |
| `acquisitionOrder` | 取得順。**コード単位でソート** |
| `fencingVerdict` | 保持者がまだ動いてよいか。3つの拒否を混ぜない |
| `nextToken` | 世代を上げる。同じ所有者が取り直しても上げる |
| `renewed` | 今から数え直す。期限を貯めない |

## 効いている理由

- **`acquisitionOrder` はデッドロックの議論**であって整頓ではない。重なる集合を欲しがる2タスクが
  必ず同じパスで最初に出会うので、片方がそこで負ける。互いに半分ずつ持って止まることがない。
  **コード単位**なのは、順序が全プロセスで同じでなければこの議論が成立しないから。
  `localeCompare` は動かす人に依存する（`common/byCodeUnit.ts` が存在する理由がこれ）。
- **`fencingVerdict` が3つの拒否を分けている**のは、runner の対応が違うから。
  `not-the-owner` は呼び手のバグ、`superseded` は誰かが奪ったのでこのタスクは止まるべき、
  `expired` は誰も持っていないので触る前に取り直す必要がある。
- **世代は所有者が同じでも上がる。** 前の保持者がまだ走っているかもしれず、
  次の書き込みを見分けられるのは番号だけだから。
