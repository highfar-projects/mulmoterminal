# キャンペーンの永続記録（#1815 PR1b）

[PR1a](feat-1815-campaign-state.md) の状態機械に、**それを記録する層**を足す。UI なし、まだ誰も import しない。

## この PR に入れるもの / 入れないもの

設計メモの PR1 は「状態機械 + store + 起動時照合 + claim-registry」だった。
PR1a で状態機械を出し、ここでは **store（記録の形式と読み書き）** までにする。

**起動時照合は入れない。** 照合が読むもの — 生きているセッション、clone の lease、
forge 上のブランチ/PR/マージ状態 — が**どれもまだ存在しない**。
無い相手を仮定して書くと、照合ではなくその相手の設計を偶然決めてしまう。
照合の純粋な判断部分は、入力が実在する PR（clone プールと forge 参照が入る回）で書く。

claim-registry は状態機械にも記録層にも依存しないので別 PR。

## 形式は `rooms.ts` / `room-log.ts` に合わせる

このリポジトリには JSONL 追記ログの型が既にある。同じ理由が同じように当てはまるので、
新しい流儀を作らない。

| 規則 | 理由（既存のもの） |
|---|---|
| 追記のみ | `MULMOTERMINAL_HOME` はこのマシンの全サーバで共有。read-merge-write は先に終わった書き手を落とす |
| 改行は**先頭**につける | 途中で切れた書き込みが壊すのは1レコードだけ。次のレコードを巻き込まない |
| パースできない行は単独で捨てる | 同上 |
| `at` で並べ替えない | 同一ミリ秒の2書き手と、逆行する時計。ファイルの順序が実際に起きた順序 |
| id 検査が path 防御の**全部** | `roomFile()` と同じ配置。全入口がこの関数を通る |

## intent → outcome

副作用（セッション起動、prompt 注入、PR、マージ、close）は**全部この プロセスの外**で起きるので、
記録と原子的にできない。だから intent を副作用の**前**に、outcome を**後**に追記する。
**outcome の無い intent が、そのままクラッシュ窓**になる。

- `settled` = 起きた。タスクは記録されたフェーズへ
- `abandoned` = 起きなかった。フェーズは動かず、attempt は使い切り

冪等キー `campaign/<id>/<task>/<attempt>` は**保存せず導出する**。
再起動時は forge と clone に「その名前のものが既にあるか」を聞けばよく、
欠けているかもしれない自分のログを信じなくて済む。

## fold は記録を信じない

`foldCampaignLog` はレコードに書かれたフェーズを採用せず、**状態機械で再生する**。
機械に無い辺を名乗る settlement は、新しい辺ではなく壊れたログである。

弾く5種（`rejected` に載せ、投げない — 壊れた行も実際の事象についてのデータで、
runner はそれを人に見せる必要がある）:

| 理由 | 何が起きた |
|---|---|
| `illegal-transition` | そのフェーズに無いイベントの intent / settlement |
| `intent-while-pending` | 1タスクに副作用が2本同時。2本目がバグ |
| `no-intent` | 誰も宣言していない書き込み |
| `wrong-event` | 未決の intent と event か attempt が違う（古い再試行が新しいものに答えるのを防ぐ） |
| `phase-mismatch` | そのイベントの行き先と違うフェーズを名乗っている |
| `attempt-reused` | 使い切った attempt をもう一度使おうとした（下記） |

**attempt はタスクごとに厳密増加する。** これが冪等キーを1回限りにする。
危ないのは `abandoned` の直後で、放棄された試行がその名前でブランチや PR を
外に残しているかもしれない。同じ attempt で再試行すると、再起動時の
「その名前のものは既にあるか」がその残骸を見つけて「もう済んでいる」と答える。

## `appendCampaignRecord` が `postToRoom` と違うところ

`postToRoom` は追記の失敗を飲み込む。こちらは **`false` を返し、呼び手は副作用を起こしてはならない**。
失われたメッセージは失われたメッセージだが、**失われた intent は誰も照合できない副作用**である。

## `true` が約束する範囲（2026-08-23 に絞った）

当初は「ホスト/電源障害を越えて残る」と書いていた。レビュー14ラウンドのうち10ラウンドが
この約束をめぐるもので、指摘は毎回正しく修正も毎回改善だったが、**この PR のどのテストも
それを検証できない**（fsync の有無を区別するには本物の電源断が要る）。
テストで支えられない約束は静かに真でなくなるので、示せる範囲に絞った。

- **約束する**: レコードは読み手に照合され、書かれ、flush された。
  つまりこのプロセスの終了を越えて残り、次のプロセスが読める
- **約束しない**: 電源断を越えること。ファイル名のエントリ、そのディレクトリのエントリ、
  と上へ続く話で、`appendCampaignRecord` は最初の1つを、`ensureCampaignStore` は
  残りを**最善努力で**同期する。実証できないので約束にはしない

`true` を電源断への証明として扱う呼び手を作らないこと。
永続化の作業自体は残してある — 説明を正確にしただけである。
