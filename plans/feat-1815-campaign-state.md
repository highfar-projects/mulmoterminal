# Campaign Mode の状態機械（#1815 PR1a）

[`future/grid-campaign-mode.md`](../future/grid-campaign-mode.md) の PR1 は
「状態機械 + store + 起動時照合 + claim-registry」を1本にしていた。
これを**独立して revert できる単位**に割る。

| | 中身 | 単独で戻せるか |
|---|---|---|
| **PR1a（これ）** | 状態機械。純関数のみ | ○（まだ誰も import していない） |
| PR1b | store（intent/outcome の追記）と起動時照合 | 状態機械に依存 |
| PR1c | claim-registry（期限つき CAS + 所有者トークン） | 状態機械に依存しない |

割る理由は、**PR1a の中身がほぼ全部「不変条件」**だからである。
設計レビューで出た 55 件のうち多数がこの状態機械の性質に関するもので、
それをテストとして固定することがこの PR の成果物になる。
store と一緒に出すと、その性質のレビューが I/O のレビューに埋もれる。

## 置き場所

| ファイル | 中身 | なぜそこか |
|---|---|---|
| `common/campaignPhase.ts` | フェーズ名、終端判定、4つの性質述語 | roster のピル（PR9）が**フェーズから表示を決める**。`common/prPhase.ts` と `src/components/rosterPhase.ts` の関係がそのまま当てはまる |
| `server/campaign/campaign-state.ts` | 遷移表と `advance()` | **サーバだけがキャンペーンを進める**（D4）。遷移表をブラウザに配ると、動かす手段を配ってはいけない場所へ配ることになる |

設計メモは `campaign-state.ts` 1本と書いていたが、`common/` 規則
（両側が決定に使う値は `common/`）が優先する。ただし遷移は片側だけのものなので分けた。

## 設計の意図

**遷移表と性質述語を、同じことの独立した2つの言明として書く。**
表は「どの辺があるか」、述語は「そのフェーズにいるタスクについて何が真か」を言う。
テストが両者を突き合わせる。

これは設計レビューの結果そのものである。同じ欠陥
（規則を1箇所に書いて、それが支配する場所へ運び忘れる）が14回出た。
散文では規則を保持できず、辺と突き合わせられる述語なら保持できる。

**辺は1本ずつ書き下す。規則から生成しない。**
`merged` と `learn` に `stop` が無いのは意図的な例外だが、
共通ケースを規則で生成すると、意図的な例外と書き忘れが区別できなくなる
（レビューで実際に4回そう読まれた）。

## 設計メモから増やしたもの

- **`done` フェーズ。** メモの図は `Learn --> [*]` で終わる。終端に名前を与えると
  「`Learn` の完了で claim を解放する」が他の解放点と同じ形の規則になる。
- **`Holding = "held" | "free" | "unknown"`。** `orphaned` の clone と `leased` の claim は
  真偽値で答えられない。レビュー52番が「入り方が2通りある状態に1つの値を書いた」
  ことを欠陥として挙げているので、型で答えられなくする。

## テスト

不変条件を、辺の全体に対して述語で確かめる:

- clone を取るのは `leased` だけ／`leased` に入るとき既に持っていない
- `stop` の辺が `isStoppable` と**両方向で**一致（欠落も余剰も落とす）
- `crash` の辺が `canCrash` と両方向で一致
- claim を手放す辺は終端行きだけ
- 作業へ戻る辺は全部 `leased` 経由で、claim を持ったまま
- 終端はどのイベントも受けない
- `intake` から全フェーズに到達できる／全フェーズから終端に到達できる
- 表に無い (phase, event) は全部 `null`

加えて、レビューで「漏れ」と読まれた非対称（`merged`/`learn` は止められないが落ちうる、
`orphaned` は先に解決する）を名前付きのテストにして、次の読み手が同じ「修正」に手を伸ばさないようにする。
