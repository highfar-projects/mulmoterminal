# feat(blueprint): コレクションの記録も写して、local のアプリに移し替える (#2514)

設計 `plans/feat-blueprint-from-collection.md`（#2480）の段階 2。

## 方針

- **質問の型 `pick: "records"`**（はい／いいえ）
  - 「コレクションを選ぶ」質問と組でしか置けない。一つのヒアリングに一つ。
  - 記録には個人情報が入り得るので、`from-collection` のヒアリングは既定値を置かずに毎回聞く。
  - `recordsWanted()` は、はい（`true`）だけを写すと読む。
- **写し**（`collectionSnapshot.ts`）
  - 記録はコア の `storeFor(collection).list()` で読む（ワークスペースと同じ根）。コレクションごとに `records.jsonl`。
  - `image` / `file` の項目が指すファイルは `files/<パス>` にバイナリのまま写す。
    - どの値を写すかは純粋な関数 `referencedFiles` で決める。相対で、`..` も空の区切りも無いパスだけ。
    - 読むときはワークスペースの実パスの内側に限る。リンクで外に出るものは写さない。同じファイルは一度だけ。
  - `source.json` に `records`（写したか）を書く。
  - 総量の上限は `MAX_SOURCE_BYTES`（200 MB）。超えたら 400 で断り、重さと「記録を写さずに始める」を伝える。上限は試験のために引数で差し替えられる。
- **表と列の名前の約束**（`spec/conversion.md`）
  - 表はコレクションの slug（`-` は `_`）、列は項目のキーのまま。
  - `ref` は参照先の主キーの値、`image` / `file` は記録のパスのまま。
  - この約束が、機械で突き合わせることを可能にしている。
- **工程 `import`**（「データの形」の直後）
  - スキル: `yarn import-source <DB>` を作り、写しの記録とファイルを入れる。何度走らせても同じ結果にする。合わない記録は黙って落とさず止める。
  - 判定 `checks/import.sh`: 一時 DB に 2 回走らせ、`import-verify.mjs` が `node:sqlite` で DB を読み、次を確かめる。
    - 件数
    - 保存する単純な型（文字・数・真偽・日付・選択・参照・画像・ファイル）の全件・全項目の値
    - `data/files/` のファイル
    - 形だけのビルドでは何もせずに通る。最後に `yarn test`。

## 確かめたこと

- 試験: 関数（記録の書き出し、パスの選別、ヒアリングの規則）、写し（記録とバイナリ、写さない場合、外を指すファイル、重複、上限）、API（記録の要否が渡る、上限超え）、移し替えの判定。
  - 判定は、代役の import を正しい版と間違えた 6 通り（件数・値・真偽を文字で・ファイル・二重登録・表名）で `sh` から動かした。
- 実物: 作業用ワークスペースに記録と画像を置き、この作業コピーのサーバーを別ポートで起動した。
  - 「記録も写す」で始めると、`books` と `authors` の記録と画像（バイト単位で同一）が写った。
  - その写しに約束どおりの移し替えを手で書いて当てると、判定が通った。1 項目を落とすと、その記録とその項目を名指しして落ちた。

## 範囲外

- `money` / `table` の値の突き合わせ。判定はこの二つの項目を見ない（記録の件数と、それ以外の項目の値は見る）。列や子の表の形が一つに決まらないため。
- firebase（段階 3）
- 共有アプリ（段階 4）
