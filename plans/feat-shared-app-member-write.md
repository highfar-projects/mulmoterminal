# 共有アプリ: 名簿の人が「書く」— 承認・担当の付け替えと、参加者の入口

**状態**: 設計（2026-08-13）。[`feat-shared-app-member-view.md`](./feat-shared-app-member-view.md)
が残した 2 つの宿題 — **メンバーからの書き込み**と**participant の入口** — を 1 つの計画にする。
どちらも同じところに着地するので分けない: 「書く」の中身は participant にもあり
（自分の予約を取り消す）、入口を決めないとその書き込みの置き場所が決まらない。

前提: [`docs/shared-app-principles.md`](../docs/shared-app-principles.md)（不変条件）、
[`feat-shareable-collections.md`](./feat-shareable-collections.md)（D1–D10）、
[`feat-shared-app-member-view.md`](./feat-shared-app-member-view.md)（`/m/{slug}`、実装済み）。

---

## 何が無いのか

受付は今、**見るだけ**でいる。`/m/{slug}` は読み、ビューが何かを送れば
「read-only」と答える。予約を承認するには、オーナーの Mac を開けて
MulmoTerminal のコレクション画面まで行くしかない — つまり D7 が読みだけで守られていて、
**書きは今でもホストが実行経路にいる**。

participant はもっと手前で止まっている。`audience: "participant"` は宣言でき、
`roster/*` にも publish され、`/staging/{aid}` からは見える。しかし
**publish 後に participant が行く URL が存在しない**。作ったページは誰にも届かない。

---

## 先に確かめたこと: ルールは変えなくてよい

これがこの計画の形を決めた。`firestore.rules` の `updateWith` は既に:

- `isWriter(r)` — owner / editor はそのコレクションのレコードを更新できる
- `isAssigned(r, c) && assignedBefore(c) && assignedAfter(c)` — assignee は
  **自分に割り当てられた行**を更新できる（受け渡しはできない）
- `ownRow(...) && selfWriteOk(c, s)` — participant は**自分の行**を、
  `selfUpdate` / `selfTransitions` の範囲で更新できる
- `transitionOk(c)` が**全員を縛る**ので、状態遷移は宣言どおりにしか動かない

そして `mail/{mailId}` の create は既に「そのコレクションの writer、または
その行の assignee」に開いていて、コメントは**この経路のために書かれている**
（「A member holding only per-collection roles … must still be able to send the approval mail」）。

**足りないのはクライアントだけ**である。ルールの手 deploy が要らないので、
この計画の依存順は前回と違う（下記）。

## 決定 1. 意図の語彙は閉じる。汎用のパッチにしない

ビューが送れるのは 2 つだけにする:

| kind | 何を書くか | 誰が通るか（ルールが決める） |
|---|---|---|
| `transition` | `collections[cid].statusField` **1 フィールドだけ** | writer / 自分の行の assignee / 自分の行の participant |
| `assign` | `collections[cid].assigneeField` **1 フィールドだけ** | writer のみ（assignee は受け渡せない） |

**汎用の `{cid, itemId, patch}` にしない。** ルールが権威であることは変わらないので、
汎用にしても「メンバーの権限を超えた書き込み」は起きない。起きるのは別のことで、
そちらのほうが直しにくい:

- **ページのバグが、そのメンバーの権限いっぱいまで届く。** 承認ボタンの実装ミスが
  氏名や電話番号を書き換えても、ルールは通す（editor なのだから）。1 フィールドに
  閉じてあれば、同じバグは「間違った状態にした」で止まる
- **監査できない。** 何が起きたかを親が言えない。`transition` なら
  「`bookings/xxx` を `approved` にした」と 1 行で言える
- **語彙は有限**（原則 10）。`audience` も `role` も `scope` も閉じた集合で、
  ここだけ開けると、次に足すものが「どの語彙に足すのか」を持たなくなる

**汎用の値の編集（`selfUpdate` の範囲でフォームを出す）は、この計画の外**。
要るときに 3 つ目の kind として足す — そのときも閉じた形で足せる。

## 決定 2. 何が書けるかは、**階層ごとに違う遷移表**として射影する

`transitions` は 2 つある。ルールが読むのは同じ `statusField` だが、
**誰の遷移か**が違う:

| 階層 | 遷移の出どころ | 意味 |
|---|---|---|
| `member` | `collections[cid].transitions` | スタッフの遷移（`pending → approved`） |
| `roster` | `public.submit[cid].selfTransitions` | 本人の遷移（`pending → cancelled`） |

だから射影も階層ごとに違うものを載せる。**同じ表を両方に載せてはいけない** —
participant のページに `approved` ボタンが出て、押すとルールに拒否される。
「見えるが押せない」は、この機構が最も避けたい失敗（宣言と実行がずれる）そのもの。

`assign` は **`member` 階層にしか無い**。`assigneeField` を持つコレクションだけが持つ。

## 決定 3. 担当の候補は射影に載せる（member 階層にだけ）

付け替え先は**アドレス**でしか指定できない（ルールが比較できるのはそれだけ）。
しかし付け替える人は名簿を読めない — `apps/{aid}` の read は `readerOf(a, '*')` で、
`bookings` だけ editor のスタイリストは**自分の同僚の一覧を持っていない**。

そこで **`member/live:config` に `assignees` を載せる**: そのコレクションに対して
`owner` / `editor` / `assignee` を持つ人のアドレス。ビューは選択肢を描き、
親は一覧に無いアドレスを拒む。

**これはスタッフのアドレスをスタッフに見せる**という判断である。書いておく:

- 載るのは **`member` 階層だけ**。participant（`roster`）には決して載らない
- 載るのは **`assigneeField` を宣言したコレクション**の分だけ
- 読めるのは `staffOf` — つまり同じ店で働いている人。同僚のアドレスを同僚が知るのは
  この機構が漏らす前から成り立っている（承認メールの差出人でもある）

自由入力にする案は採らない。名簿に無いアドレスを書くと、**その行は誰にも
書けなくなる**（assignee 分岐は `assignedBefore` を要求するので、当人以外は届かない）。
拒否できる場所があるのに黙って壊れるほうを選ぶ理由が無い。

## 決定 4. 確認ダイアログは出さない

公開ビューの submit は、送る内容を親が保持して**訪問者に確認させてから**書く。
メンバーの意図では**出さない**。

公開側で確認が要るのは、**ページを書いた人と、責任を負う人が違う**から —
オーナーの HTML が見知らぬ訪問者のブラウザで走り、訪問者は自分が何に同意したのかを
知る必要がある。メンバー側はそこが逆で、ページもデータもメンバーの店のもので、
権限の上限はその人のロールが決めている。1 日に何十回押すボタンの前に
モーダルを置くのは、機構の安全性を上げずに使うのをやめさせるだけになる。

**代わりに結果を必ず言う。** 何が起きたか（どのコレクションのどのレコードを
何にしたか）と、拒否ならその理由を、ページの外側（親のバー）に出す。
ページが「成功しました」と描くかどうかに依存させない — それはページの自由で、
嘘を書けるのはビューの側だから。

## 決定 5. participant の入口は `/p/{slug}`。`/a/{slug}` を分岐させない

前の計画では「`/a/{slug}` にサインイン後の自分の行」が**推奨・未確定**だった。
**採らない。**

`/a/{slug}` の保証は「サインアウトのまま描ける・アプリの内部語彙を出さない」であり、
D10 はこれを分岐で薄めないと言っている。サインイン状態で別のものを描くページは、
その保証を「たいてい成り立つ」に変える。`/m/{slug}` を分けたのと**同じ理由**で、
同じ答えを出すのが筋が通る。

| URL | 誰の | 階層 | 述語 |
|---|---|---|---|
| `/a/{slug}` | 匿名の訪問者 | `config/*` | `allow read: if true` |
| `/m/{slug}` | ロールを持つ人 | `member/*` | `staffOf` |
| `/p/{slug}` | 名簿にいる人 | `roster/*` | `listedIn` |

**`/p/` の中身は `/m/` と同じ実装**（`useMemberApp` が階層を引数に取る）。
違うのは読む階層だけで、「開けるか」の判定も、id 付きの共有リンクも、
知らない id と開けない id を同じ答えにするのも、そのまま効く。

**`/m/` と `/p/` は排他ではない。** スタッフが同時に participant であるアプリはある
（自分も予約する店主）。`/m/` は `member` だけ、`/p/` は `roster` だけを見るので、
両方に行けて、それぞれが別の顔を出す。これは分岐ではなく**別の入口**である。

`/a/{slug}` には**小さな導線**を置く（「スタッフの方はこちら」の隣に「参加者の方はこちら」）。
リンクはサインイン状態を見ない — 見た瞬間に分岐になる。

## 設計

### 意図はチャンネルを逆向きに通るだけ

公開ビューの submit と**同じ機構**（`viewChannel` の MessagePort、per-render nonce、
`__MC_APP_VIEW`）。増えるのはメッセージの型 2 つと、その答え:

```text
mc-app-view:intent   { requestId, kind, cid, itemId, to }
mc-app-view:result   { requestId, ok, reason? }
```

`ready` / `state` は今のまま。**ビューは Firestore に触れない**（公開ビューと同じ）。

### 親が言えることと、ルールにしか言えないこと

親のチェックは**拒否の理由に名前を付ける**ためにある。ルールは同じものを一瞬後に
拒むが、その拒否は何も名指さない。順に:

| 拒否 | 何を見て | なぜ親が見るのか |
|---|---|---|
| `not-an-intent` | 形 | 答えない（誰も訊いていない） |
| `unknown-collection` | 射影の `views[].collections` に無い | ページが宣言していないものを書こうとしている |
| `not-writable` | その階層にその kind の宣言が無い | `statusField` / `assigneeField` が無い |
| `illegal-transition` | 階層の遷移表に `to` が無い | 押せてはいけないボタンが描かれている |
| `unknown-assignee` | `assignees` に無い | 書けば誰にも書けない行になる |
| `denied` | ルールが拒否した | ここだけは親には分からない — 権限、遷移の競合、`immutable` |

**`illegal-transition` は親の表で判定するが、親の表は古くなりうる**
（データセットを渡した後に誰かが承認した）。その場合はルールが拒み、`denied` になる。
**それでよい** — 親の表は「描かれるはずのないボタン」を捕まえるためのもので、
競合の権威ではない。権威は 1 か所（ルール）のまま。

### 承認メールは書き込みの一部ではない。別の書き込みで、再送が安全

`collections[cid].mail` を宣言したコレクションでは、承認が承認メールを伴う。
これは**同じ書き込みにできない** — `mail/` と `items/` は別のドキュメントで、
バッチにしてもルールは互いの存在を要求しない。

代わりに**順に 2 回書く**。片方だけ通った状態が起きるので、そのときどうなるかを決める:

- **レコードが先、メールが後。** 逆にすると「承認していないのに承認メール」が起きる
- **メールの id は決定的**（`{cid}_{itemId}_{template}`、ルールが強制する）。
  だから**再送は安全**で、同じ承認から 2 通は出ない。失敗したら「メールが出ていません、
  もう一度」と言えて、押しても壊れない
- メールが出せなかったことは**必ず言う**。黙って成功にすると、
  受付は客に連絡が行ったと思う

### staging は今のまま両方を見る

`/staging/{aid}` は既に `member` と `roster` の両方を読んで合わせる。
意図もそこから送れる — **staged のページが live のレコードを書く**ことになるが、
これは意図的で、既にそうなっている（`/staging/{aid}` は本物のレコードを見せている）。
「公開前にスタッフの画面を試す」が試せなくなるほうが困る。

## リポジトリ横断と依存順

**ルールの変更は無い**（上記）。だから手 deploy を待つ段が無く、順は 3 つ:

| | 1 宣言・射影 | 2 ランタイム | 3 ホスト |
|---|---|---|---|
| mulmoclaude core | 階層ごとの遷移表・`assignees`・`mail` を `{tier}/config` に載せる | — | — |
| mulmoserver | — | 意図の受け口、`/p/{slug}`、`/a/` の導線 | — |
| mulmoterminal | — | — | テンプレート、スキル、publish のテスト |

**2 は 3 より先**（前回と同じ理由: 古いランタイムに新しい射影を publish すると、
名簿の人は「何もありません」を見て、publish した本人には成功に見える）。
**1 は 2 より先**（射影が無ければランタイムは何も判定できない）。

順序:

1. **core**: `AppViewConfigDoc` に `write` を足す。階層ごとに、コレクションごとに、
   `statusField` / 使える遷移 / `assigneeField` / `assignees` / `mail`。
   `projectAppViews` が階層で出し分ける。門は既存（`normalizeViews`）に乗る
2. **mulmoserver**: `viewConfigFrom` が `write` を読む。意図の判定
   （`appIntent.ts`、`publicViewMessage.ts` と同じ形の純関数）。
   書き込み（`updateDoc` 1 フィールド、続いて `mail` の create）。
   `AppViewFrame` が結果を返す。`/p/{slug}` と `/p/{slug}/{id}`。`/a/` の導線
3. **mulmoterminal**: `mulmoterminal-shared-app` スキルとテンプレートに
   「承認できるページ」の書き方。publish 側は core の射影をそのまま書くので
   コードは増えない — 増えるのは**テスト**（階層ごとに違う遷移表が出ることを固定する）

## やらないこと

- **汎用のフィールド編集**（`selfUpdate` のフォーム）。3 つ目の kind として後で
- **participant の書き込みを `member` と別扱いする。** 同じ `transition` で、
  遷移表が違うだけ。分けると同じものが 2 つの名前で 2 か所に書かれる
- **`/a/{slug}` をサインインで分岐させる**（決定 5）
- **名簿そのものを射影する。** 載るのは `assigneeField` を持つコレクションの
  担当候補だけで、ロールも、他の participant も、載らない
- **削除**。`deleteWith` は既に開いているが、ビューから消せるようにする理由が今は無い

---

## 開いている問い

- **`assignees` の粒度。** いまの案はコレクションごと。アプリ全体で 1 つにすると
  射影は小さくなるが、「この店の担当になれる人」と「この一覧の担当になれる人」が
  違うアプリで嘘になる
- **メールの再送を誰が押すのか。** 親のバーに出す案と、ビューに `mail` の失敗を
  返して描かせる案がある。後者は「ページが嘘を描ける」に触れる
- **`/p/{slug}` に行くべき人が `/m/{slug}` を開いたとき。** いまの答えは
  「あなた向けのページはありません」。もう一方の入口を案内すると、
  そちらに何かがあることを言うことになる — 名前の解決で「無い」と
  「名簿にいない」を区別しないのと同じ問いで、まだ決めていない
