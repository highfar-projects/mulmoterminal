# fix: /api/git-status のポーリングに多重起動ガードを入れる (#2164)

## 何が壊れているか

`git status --porcelain` がサーバ配下で同時に数十本走り、マシンを飽和させる。
仕事そのものは小さく（計測した1本は出力35行、CPU約10秒）、実時間の大半は
互いの競合待ちだった。同時実行が増えるほど1本が遅くなり、遅くなるほど重なる。

原因は concurrency control が一段も無いこと:

| 場所 | 状態 |
|---|---|
| `src/composables/useGitStatus.ts` | `req` トークンは遅延応答を捨てるだけ。実行中でも次を撃つ |
| `src/composables/usePollWhileVisible.ts` | `setInterval` が実行中を見ずに発火 |
| `server/git/git-status.ts` | cwd 単位の合流なし。セルが同じ checkout を開いていると独立に git を起動 |

## 直し方

ひとつの不変条件を二箇所で守る: **同じ cwd の git status は同時に1本だけ**。

### 1. クライアント: ポーリングは実行中ならスキップする

`useGitStatus` に実行中カウンタを持ち、**ポーリングのティックだけ**を抑制する。

- `watch(cwd, refresh)` は抑制しない。cwd が変わったら別の問いなので、必ず投げる
- 公開している `refresh`（ターン終了直後の強制更新）も抑制しない。意図的な要求なので通す
- 既存の `req` トークンはそのまま。役割が違う（遅延応答の破棄）ので置き換えない

### 2. サーバ: 同じ cwd の同時リクエストを1本に合流させる

`coalesceByKey` を独立ファイルに切り出し、`gitStatus` から使う。

- **キャッシュではない**。エントリは実行中だけ生存し、決着したら消える。
  したがって合流窓は「1回の計算の所要時間」ちょうどで、これまで1回の呼び出しが
  持っていた以上の古さは生じない
- issue に書いた「TTL をどれくらいに置くか」は **0（合流のみ）** を選ぶ。
  短いキャッシュは別の判断として切り離せる

クライアント側だけだとセルをまたいだ重複が残り、サーバ側だけだと1セルが
撃ち続ける分が残る。効き幅はサーバ側が大きいが、両方で初めて上の不変条件になる。

## テスト

- `coalesceByKey`: 単体で網羅する（同時呼び出しが1回に合流する / 決着後は再実行される /
  キーが違えば合流しない / 同期throw が rejection になる / rejection 後にエントリが消える）
- `useGitStatus`: 実行中のティックが fetch を増やさないこと、
  cwd 変更と明示 refresh は抑制されないこと
- `gitStatus`: 同じ cwd への同時呼び出しで git 起動回数が増えないこと

## 検証で確かめられないこと

このコードは全セルの git status 経路にあたるため、ユニットテストだけでは
「アプリが起動してヘッダのブランチ表示が出続けるか」は担保できない。
PR にどこまで実機で確認したかを明記する。
