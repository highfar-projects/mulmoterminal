# feat(blueprint): コレクション・共有アプリを、設計図で本格的なアプリに仕上げる (#2480)

設計の段階。実装は下の「段階分け」ごとに issue と PR を分ける。

## 何を作るのか

コレクション（`schema.json` で宣言したデータと画面）や共有アプリ（`app.json` を持つリポジトリ）を元に、設計図で**自分のコードとして持つアプリ**を作る。土台は今ある `local`（Express + SQLite + Vue）と `firebase`。のちに Supabase・Cloudflare の土台を足す。

### 位置づけ

コレクションと共有アプリは、宣言だけで作る試作と小さな運用のためのもの。共有アプリの設計（`plans/feat-shareable-collections.md` の「宣言で表現できる範囲」）は、宣言で書けない要求が増えると HTML に真実が移って劣化する、と書いている。

この機能は、その先の**卒業先**になる。宣言で書けなくなったとき、自分の基盤で動かしたいとき、コードとして持ちたいとき、その時点の姿を仕様書に落とし、今の設計図の工程でコードにする。

- 元のコレクション・共有アプリには**触れない**。取り込むのはその時点の写し。
- 双方向の同期はしない。卒業したら、元は元、新しいアプリは新しいアプリ。

## 決めたこと

| 論点 | 決定 |
|---|---|
| 元の範囲 | 手元のコレクションに加え、**共有アプリまで**含める（複数のコレクション、メンバーと役割、公開の申込み、Firestore 上の記録） |
| 入口 | **設計図のフォームだけ**。コレクション画面にボタンは置かない |
| アクション・自動取り込み | **普通の機能に書き換える**。エージェントに頼んでいた処理も、アプリの機能として仕様に起こす |

## 全体の流れ

1. 設計図の「新しく作る」で、種類「コレクションからアプリにする」を選ぶ。土台は `local` か `firebase`。
2. 最初の質問で元を選ぶ（新しい質問の型 `pick: "collection"`）。候補は次の二つ。
   - 手元のコレクション（`GET /api/collections/list` と同じ探し方）
   - 共有アプリ（`app.json` を持つフォルダ）
3. 「始める」で、元の写しをビルドのフォルダの `.blueprint/source/` に置く（下の「写しの形」）。
4. ヒアリングは、元から分かること（アプリ名、扱うもの、項目、画面）を先に埋め、残り（誰が使うか、ログイン、必須の機能、アクションの置き換え方）だけを聞く。
5. 仕様書の工程が、写しを読んで仕様書を書く（下の「変換」）。移らないもの・形が変わるものは「決めていないこと」に並べ、人が承認の前に読めるようにする。
6. 土台の工程がアプリを作る。途中に「記録の移し替え」の工程が入る。
7. 最後は今の約束どおり、セキュリティ診断 → 使い始め方（`start-here.md`）で終わる。

## 写しの形（`.blueprint/source/`）

```
.blueprint/source/
  source.json                 何を・いつ・どこから取ったか、コレクションごとの記録の件数
  app.json                    共有アプリのときだけ
  collections/<slug>/
    schema.json
    SKILL.md
    views/*.html              宣言されたカスタムビュー
    templates/*.md            アクション・取り込みの指示
    records.jsonl             記録。1 行 1 件
  files/                      image / file 型が指す画像やファイル（参照されているものだけ）
```

- **手元のコレクション**: `loadCollection` で読み、`storeFor(...).list()` で記録を取る。`ref`・`embed`・`backlinks`・`rollup` が指す別のコレクションも一緒に取る（指す先が無ければ、仕様書の「決めていないこと」に出す）。
- **共有アプリ**
  - `app.json` と、`storage: firestore` のコレクションをすべて取る（`sharedCollections(root)`）。
  - 記録は、著者がサインインしているセッションで Firestore の `apps/{aid}/collections/{cid}/items` から読む。管理者の鍵は使わない。
  - 読めるのは、ルールがその人に許す範囲だけ。owner・editor・viewer でなければ全件は読めないので、取り込みを断り、理由を出す。
  - サインインしていなければ「先に接続してください」で断る（既存の `sharedCollections.ts` と同じ）。
- 置き方は、見本のファイルを置く仕組み（`server/blueprint/samples.ts`）と同じ約束に従う。既存のファイルは上書きしない、衝突したら何も書かない、途中で失敗したら作ったものを消す。ただし入れ子のフォルダとバイナリ（画像）を扱う別の置き方になる。
- **個人情報**: 記録を新しいフォルダに写すことになる。フォームで「記録を写す／形だけ写す」を選べるようにし、形だけのときは記録の移し替えの工程を飛ばす。

## 変換

仕様書の工程のスキルは、次の対応表に従って書く。表は仕様書にも載せ、人が読めるようにする。

### 項目の型

| コレクション | local（SQLite） | firebase（Firestore） |
|---|---|---|
| string / text / email / markdown | TEXT（email は形を検査、markdown は画面で整形して表示） | string |
| number | REAL（整数だけなら INTEGER） | number |
| money | 金額は INTEGER（最小単位）＋通貨の列 | 同じ形の map |
| boolean | INTEGER 0/1 | boolean |
| date / datetime | TEXT（ISO 8601） | string（ISO）または Timestamp。仕様書で決める |
| enum | TEXT ＋ 値の CHECK 制約 | string ＋ ルールで値を制限 |
| image / file | ファイルは `data/files/`、列にはその中のパス | Storage ＋ Storage のルール |
| ref | 外部キー | 参照先の id ＋ ルールで存在を確かめる |
| table | 子の表（親への外部キー） | サブコレクション、または配列の map（件数による） |
| derived | 保存しない。API で計算して返す | クライアントで計算して表示 |
| rollup / backlinks | 集計・逆引きの問い合わせ | クエリ（集計が重ければ関数で持つ値） |
| embed / toggle / flag | 保存しない。画面の表示の仕様になる | 同じ |
| `when` | 画面で条件付きで表示する（値は消さない） | 同じ |
| `required` / `primary` | NOT NULL / 主キー | 必須はルールで検査、主キーは doc id |

### 画面

- 既定の一覧・詳細・入力フォームは、そのまま画面の仕様になる。
- `displayField` は一覧の見出し、`kanbanField` はカンバン画面、`calendarField` / `calendarEndField` / `calendarTimeField` はカレンダー画面になる。
- `completionField` / `triggerField` / `notifyWhen` は、完了の状態と期日の通知になる。通知の方法（画面内・メール）は仕様書で決める。
- カスタムビュー（`views/*.html`）は、写しに残して仕様書から参照する。画面は土台の画面（Vue）として作り直し、HTML はそのまま使わない。

### アクションと自動取り込み（普通の機能に書き換える）

| 元 | 書き換え先 |
|---|---|
| `mutate`（`set` / `require` / `params`） | API の操作 ＋ 画面のボタン。`require` は API の入口で検査 |
| `chat` / `agent`（`templates/*.md`） | テンプレートの中身を読み、アプリの機能として仕様に起こす。AI が要る処理は、ヒアリングでどうするかを聞く（Claude の API を呼ぶ機能にする／人が手で行う操作にする／やめる） |
| `ingest`（rss / atom / http-json） | 定期取り込みの処理。local はサーバー内の定期実行、firebase は定期実行の関数 |
| `ingest`（agent） | `chat` / `agent` と同じ扱い |

### 共有アプリの権限

`app.json` の宣言は、仕様書の「誰が何をできるか」の表になる。これはそのまま、土台のログイン・役割・ルールの工程の入力になる。

| app.json | 仕様書での扱い |
|---|---|
| `members`（email → 役割）、役割 owner / editor / viewer / participant / assignee | 役割の表。初期のメンバーとして移す |
| `collections[cid].statusField` / `transitions` / `immutable` / `sealed` | 状態の遷移と、変えてはいけない項目。サーバー（local）またはルール（firebase）で強制する |
| `peerVisibility` / `revealGated` / `revealBy` / `participantRead` | 他の人の記録が見えるか。見える範囲の表 |
| `public.submit[cid]`（`auth`・`idFrom`・`finalize`・`window`・`selfUpdate` など） | 公開の申込みフォーム。一人一回（`idFrom` が本人の uid）、書き切り（`finalize`）、期限（`window`）は、サーバーやルールの規則として仕様に書く |
| `public.view` / `views[].audience` | 公開の画面と、その見える範囲 |
| `mail` | メールの通知。local は送り方を仕様書で決める（SMTP の設定）、firebase は Trigger Email 拡張か関数 |
| `aggregate` / `live` | 集計の表示と、ライブ更新の要否 |

## 設計図の側に足すもの

- **種類のパック** `blueprints/from-collection/`（名前は仮）: `bases: ["local", "firebase"]`、`hearing.json`、`steps.json`、仕様書の工程のスキル、記録の移し替えのスキル。
- **質問の型** `pick: "collection"`: `pick: "files"` と同じ並びに足す。答えは元を指す値で、フォームが候補を出す。サーバーは始めるときに、その値が本当に候補にあるかを確かめる。
- **写しの置き方**: `server/blueprint/` に、コレクション・共有アプリを読んで `.blueprint/source/` に置く関数を足す。どれを置くかを決める部分は純粋な関数に分けて試験する。
- **記録の移し替えの工程**（土台ごとに、種類の工程として差し込む）
  - local: `records.jsonl` を読んで SQLite に入れるスクリプトと試験。
  - firebase: エミュレータに入れて確かめ、本番へは本番公開の承認のあとで入れる。
  - 判定: コレクションごとに件数が一致し、全件の全項目が変換表どおりに元と同じ値で読み戻せる。
- 残りの工程は土台のものをそのまま使う。

## 工程の並び

- **local**: 仕様書 → 道具 → 雛形 → データ → **記録の移し替え** → API → 画面 → ログイン → 起動確認 → 必須の機能の試験 → セキュリティ診断 → 引き継ぎ（使い始め方）
- **firebase**: 仕様書 → 道具 → プロジェクト → 雛形 → ログイン → データとルール → **記録の移し替え（エミュレータ）** → 機能 → 試験 → 開発用に公開 → 保護 → セキュリティ診断 → 本番に公開 → **記録の移し替え（本番）**

## 段階分け（それぞれ issue と PR を分ける）

1. **元の選択と写し**（#2502）
   - 質問の型 `pick: "collection"` と写しの置き方（手元のコレクションだけ、形だけ）。
   - 種類のパック `from-collection`（local）。変換表と、元の全項目・ビュー・アクションが仕様書に出ることの判定。
2. **記録の移し替え（local）**（#2514）
   - 記録の写し（`records.jsonl`、「記録も写す／形だけ写す」の選択）と、移し替えの工程と判定。
   - 段階 1 で記録を写さないのは、移し替えの工程が無いまま写すと、使われない個人情報を置くだけになるため。
3. **firebase への卒業**（#2521）: Storage、ルール、エミュレータと本番への移し替え。
4. **共有アプリ**
   - `app.json` と Firestore の記録の写し。
   - 権限の表への変換。
   - 公開の申込み・メール。
5. **アクションと自動取り込み**: 普通の機能への書き換え。
6. **新しい土台**: Supabase、Cloudflare。それぞれ土台のパック。最後にセキュリティ診断と使い始め方を置く約束は、`packs.spec.ts` の `WEB_BASES` に入れて同じく守らせる。

## 決めていないこと・注意

- 大きな記録や画像の多いコレクションの写しの上限（件数・容量）。超えたらどうするか。
- 共有アプリの記録の中の個人情報（申込者のメールなど）を写すことの確認の出し方。
- MulmoClaude と同じワークスペースを読むので、写しは読むだけにし、元の書式は変えない（`CLAUDE.md` の「MulmoClaude is the reference host」）。
- 変換表のうち `date`/`datetime` の Firestore での持ち方、`table` をサブコレクションにするか配列にするかは、仕様書の工程で件数を見て決めるか、先に決め打つか。
- 写しを取った後に元が変わった場合の扱い（取り直すか、そのまま進めるか）。

## 範囲外

- 元への書き戻し、双方向の同期。
- コレクション画面からの入口（決定どおりフォームだけ）。
