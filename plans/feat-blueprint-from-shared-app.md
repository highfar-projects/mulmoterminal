# feat(blueprint): 共有アプリも元に選べるようにする (#2532)

設計 `plans/feat-blueprint-from-collection.md`（#2480）の段階 4。

## 方針

- **選択欄**
  - `GET /api/blueprints/collections` は、コレクションに加えて共有アプリも返す（`kind: "collection" | "app"`）。
  - 共有アプリは、`listProjectRoots()`（ワークスペースと保存したフォルダ）のうち、`app.json` と共有コレクション（`sharedCollections(root)`）を持つもの。
  - 値は `app:<プロジェクトの ID>`（`common/blueprint/sharedAppSource.ts`）。パスは答えに載せず、一覧に出した ID しか開かない（`sharedAppsProvider.ts`）。
  - フォームは「コレクション」と「共有アプリ」の見出しで分けて並べる。
- **写し**（`collectionSnapshot.ts`、`collectionSource` は設定オブジェクトを受ける形にした）
  - 共有アプリはアプリ全体を写す。中身は `app.json`（`.blueprint/source/app.json`）と、全共有コレクションの形。`source.json` の `from` は `app`、`start` はアプリの名前。
  - 記録は、そのアプリのフォルダを根に `storeFor(...).list()` で読む。Firestore は、著者のサインインで読む。
    - サインインしていなければ `signed-out` として 409 で断る。
    - 全件を読める役割（owner / editor / viewer）でないコレクションがあれば `not-a-reader` として 409 で断り、そのコレクションを名指しする。ルール上、それ以外の役割は一部しか読めず、黙って欠けた写しになるため。
    - 役割は、そのコレクションの役割、無ければアプリ全体の役割で決める。アドレスの大文字小文字は区別しない（`collectionsNotFullyReadable`）。
  - 形だけなら、サインインは要らない。
- **仕様書**
  - 雛形に「誰が何をできるか（元が共有アプリのとき）」の節を足した。変換表に「共有アプリの権限」の節を足した。
  - 判定は、`from: "app"` なら `app.json` の宣言ごとの名前を求める（`app.members` / `app.collections.<cid>` / `app.public.submit.<cid>` / `app.public.view` / `app.views.<id>`）。メールアドレスは仕様書に書き写させない。

## 確かめたこと

- 試験: 次を確かめた。
  - 役割の判定（アプリ全体、コレクションごとの上書き、一部しか読めない役割、壊れた名簿、大文字小文字）。
  - 共有アプリの提供元（`app.json` や共有コレクションが無いフォルダは出さない、名前の決め方、一覧に無い ID は開かない）。
  - 写し（一覧の並び、アプリ全体の写し、サインイン無しでも形は写せる、サインイン無し・役割不足で記録を断る、記録はアプリのフォルダから読む）。
  - API（2 つの断り方）、選択欄の部品（見出しの分け方）、仕様書の判定（宣言の名前が欠けると落ちる、元がコレクションなら求めない）。
- 実物: 作業用の HOME の設定に共有アプリのリポジトリを保存したフォルダとして登録し、この作業コピーのサーバーを別ポートで起動した。
  - 一覧に「議会の投票」が `app:<ID>` で出た。
  - 形だけで始めると、`app.json` と 2 つのコレクションが写り、`source.json` は `from: "app"` になった。
  - 記録も写すと、サインインしていないので理由を付けて断られた。
  - その写しに仕様書の判定を当てると、宣言の名前が欠けると落ち、揃うと通った。

## 確かめていないこと

- サインインした状態での記録の写し（remote-host の接続が要る）。
- エージェントが実際に権限を仕様書とルールに起こすビルド。
