# fix #1634 — ロケール名が無い pty で日本語が `_` になる

## 症状

Claude の出力の日本語が、幅ぶんのアンダースコアの連続になる。Claude Code のバナー
(`▐▛███▜▌`) も `_______` になる。一方その周りの罫線 (`─│`) と `·` だけは正常に見える。

## 原因

tmux の**クライアント**が pty へ書き出す瞬間の置換 (`tty_check_codeset`)。

クライアントが UTF-8 でないと判定されると、tmux は
- DEC ACS に対応のある文字は ACS に置き換え (`─` → `q`、`·` → `~`) — xterm.js は正しく描画する
- 対応の無い文字は**セル幅ぶんの `_`** に置き換える (`memset(..., '_', width)`)

全角は幅 2 なので 1 文字につき `_` 2 個。`日本語テスト` (6文字) → `____________` (12個)。
罫線だけ無事という非対称は、この ACS 代替の有無から来ている。

判定は tmux のクライアント側で `LC_ALL` → `LC_CTYPE` → `LANG` の順に最初の非空の値を見て、
その**文字列**に `UTF-8` / `UTF8` が含まれるかどうかで決まる。実測 (tmux 3.6a / macOS):

| クライアントの env | `#{client_utf8}` | pty に書かれるバイト |
|---|---|---|
| ロケール名なし | `0` | `_____ \| <ACS>qx \| ____________` |
| `LANG=C` | `0` | 同上 |
| `LANG=en_US.UTF-8` | `1` | 正しい UTF-8 |
| `LANG=zz_ZZ.UTF-8` (存在しないロケール) | `1` | — 名前の文字列しか見ていない |

ロケールが消える経路: GUI から起動されたプロセスは launchd の環境を継承する。この
マシンでも `launchctl getenv LANG` / `LC_ALL` / `LC_CTYPE` はすべて空。間に補うものが
無いので、`ptyEnv()` が返す環境にもロケール名が一つも無い。

MulmoTerminal は pty の中で `tmux new-session -A` を実行している (`pty-spawn.ts`) ので、
**pty の中身がそのクライアントそのもの**。リポジトリ全体でロケールを設定している箇所は
無い (`pluginRuntime.ts` が読むだけ)。

## なぜ #1634 で tmux が無罪だと結論してしまったか

置換はクライアントの描画経路でしか起きないのに、検証がそこを通っていなかった。

| 使った検証 | 実際に見ていたもの |
|---|---|
| `capture-pane -p` | **サーバのバッファ** — 常にクリーンな UTF-8。壊れている最中でもクリーン |
| `new-session -d` | **クライアントが存在しない** — 描画経路を通らない |
| `show-environment -g` | **サーバ**の env — 効くのはクライアントの env |

「ブラウザ再読込で直った」も同じ理屈で説明できる。リプレイは `tmuxCaptureStyledPane`
(= `capture-pane -e`) でサーバのバッファから画面を作り直すため。

## 直し方

2 つ入れる。片方だけでは残る穴がある。

### 1. ロケール名が一つも無いときだけ `LANG=en_US.UTF-8` を補う

`server/infra/pty-env.ts` に `withFallbackLocale(env, platform)`、`ptyEnv()` に配線。
ここが全ての pty (tmux クライアント / 直接 pty) が通るチョークポイント。

- **一つも無いときだけ**。`LC_ALL` と `LC_CTYPE` は `LANG` より優先されるので、既に
  それらがある環境に `LANG` を書いても何も変えられない。`LANG=ja_JP.UTF-8` を設定した
  ユーザの指定もそのまま残す
- 空文字は名前として数えない (ログインシェルが実際の `LC_ALL` と一緒に空の `LANG=` を
  export することがある)
- `withoutUnset` の内側に置く → 明示的な unset が優先される
- **Windows は対象外**。同種の慣習も tmux も無く、git-bash が `LANG` を読むため、
  元々無かった変数を持ち込むのは別の不具合の種になる
- 値が `en_US.UTF-8` なのは tmux 自身が最初に試す名前だから。仮にその名前のロケールが
  実在しない環境でも、クライアントの判定は名前の文字列しか見ていない (上表) ので
  描画の修正は効く

これは tmux 以外にも効く。ロケールを見て出力エンコーディングを決めるもの (Python の
stdout、ncurses の TUI) は同じ影響を受けている。

### 2. tmux クライアントに `-u` を渡す

`tmuxNewSessionArgs` に追加。1 が意図的に直さない穴 —— `LANG=C` のように**非 UTF-8 の
名前が明示されている**場合 —— を埋める。実測で `LANG=C` でも `client_utf8=1` になる。

ここで無条件に強制してよいのは、このクライアントの出力の読み手が xterm.js であり、
xterm.js は常に UTF-8 だから。ユーザの端末が何であるかの推測ではなく、こちらが端末を
所有している。

## 残る限界

tmux の**ペイン**の環境は tmux **サーバ**から来る。サーバは最初にそれを起動した
クライアントの環境を継承するので、この修正は次にサーバが起動する分から効く。既に
ロケール無しで動いているサーバは、再起動されるまで古い環境をペインに渡し続ける。
`-u` が直すクライアント側の描画には影響しない。

## 検証

- `pty-env` / `tmux` の spec に、実装前に落ちることを確認したケースを追加
- pty を作って実際に tmux クライアントを起動し、置換の有無をバイト列で比較
- 実アプリを起動し、ロケール名を落とした環境でセルに日本語を出して画面で確認
