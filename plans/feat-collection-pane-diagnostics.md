# コレクションペインで起きたことを、そのまま貼れる塊にする

**状態**: 提案（着手前）
**日付**: 2026-08-14
**前提**: [`plans/feat-shared-app-preview.md`](./feat-shared-app-preview.md)（手元で参加者の画面を動かす）、
[`plans/feat-shared-app-view-diagnostics.md`](./feat-shared-app-view-diagnostics.md)（公開後に事実を運ぶ経路）、
[`docs/shared-app-principles.md`](../docs/shared-app-principles.md)、
そして **MulmoClaude の `server/utils/diagnostics/report.ts`**（先例。下の「既にある足場」）

この計画が答える問いは 1 つ:

> **ペインの中で何かが動かないとき、ユーザーが隣のセルの agent に渡せるものが
> 「動かない」という一言しかない。**

デバッグに要る事実 — どの API がどう答えたか、何が投げられたか、そもそも要求が飛んだのか —
は**全部このマシンの中にある**。集めて、1 回のコピーで運べる形にすればいい。

---

## なぜ「fetch を包む」では足りないか — 1 つのペインに実行文脈が 3 つある

ここが設計の骨格で、素朴な実装が必ず外すところである。

| | 何が描かれているか | どこでコードが走るか | 「API 呼び出し」の意味 |
|---|---|---|---|
| **A** | `@mulmoclaude/collection-plugin/vue` の一覧・詳細・フィード | **シャドウ DOM**（`PluginFrame.vue`）。ホストと同じ window | ホストの window から出る `fetch` |
| **B** | コレクションのカスタムビュー（`__MC_VIEW`） | **iframe**（不透明オリジン、CORS preflight つき） | **フレームの中**から、スコープ付きトークンでホストの API を叩く |
| **C** | 共有アプリのプレビュー（`__MC_APP_VIEW`、[プレビュー計画](./feat-shared-app-preview.md)） | **srcdoc の sandbox**、CSP は `connect-src 'none'` | **API を呼ばない**。ポート越しの要求と、親の答えだけ |

`window.fetch` を包む実装は **A しか捕まえない**。B はフレームの中なので見えず、C はそもそも
ネットワークを使わない。3 つを 1 つのバッファに集める設計にしないと、「ペインの診断」を名乗って
実際には 3 分の 1 しか記録しないものになる。

## 既にある足場 — MulmoClaude を先に見る

CLAUDE.md の規則（**MulmoClaude はリファレンスのホストである**）に従って探すと、**同じ問題に
既に答えが 1 つある**:

- `/api/diagnostics/report`（`src/config/apiRoutes.ts` — 経路名の権威）と
  `server/utils/diagnostics/report.ts`。バグ報告に貼る環境レポートを**サーバ側で組み立て、
  allow list で伏せる**。
- その冒頭コメントが、この計画の一番大事な設計判断をそのまま言っている:

  > mulmoterminal の同等のスキルは `*_KEY` を伏せろと**散文で**モデルに頼んでいる。同じやり方は
  > ここではもっと悪い（…）**prompt の中にしか無い規則はテストできない**ので、コードに置き、
  > マスクの判断を純関数にする。

そして名指しされている通り、`mulmoterminal-bug-report` の SKILL.md には今も
`# mask before quoting` と書いてある。**この計画はその指摘に対する MulmoTerminal 側の答え**でもある。

したがって:

- 経路は **MulmoClaude の名前空間に合わせる**（`/api/diagnostics/*`）。新しいのは
  「環境」ではなく「**このペインで直前に起きたこと**」なので、`report` の隣に別の名前で置く。
  同じものを MulmoClaude が後で欲しがる形にしておく。
- **マスクはコードで、純関数で、テストつき。** 散文の指示に戻さない。

## 1. 一次資料はサーバ側の記録（MulmoTerminal だけが持てる利点）

公開ビューの診断（mulmoserver 側）と決定的に違うのは、**その API を出しているのが我々のホスト
自身**だということである。だからフレームに一切触らずに、B の呼び出しまで記録できる。しかも
**ページが答えを握り潰しても残る** — 診断計画の #3（答えを捨てている）に一次資料で答えられる。

記録する 1 件は:

```
+0.000  GET  /api/collections/{slug}/view-data        200   18ms  items=42
+0.412  PUT  /api/collections/{slug}/view-data        200   31ms  written=0 rejected=1
+0.415  !    rejected: id=r-7 problem="`attendees` must be a number"
```

- クエリは**キーだけ**（値は既定で出さない）。
- **200 で失敗している形を、失敗として数える。** このリポジトリの API は
  `{ error }`・`{ rejected: [...] }`・`{ written: [] }` を 200 で返す（`viewDataPutHandler`）。
  status だけを見る記録は、診断計画が名指した「答えを捨てている」種類の不具合を**記録の側でも
  もう一度捨てる**。どのフィールドが失敗を意味するかは、**経路ごとに宣言する**こと。
- 足す場所は既にある。`guarded()` が throw を 500 にしてログしているので、その隣に輪バッファを置く。
  **記録するのはコレクション/ビュー系の経路だけ**で、ターミナルや WS の経路には触らない。

## 2. 二次資料はクライアント側の記録（サーバに届かなかったもの）

一番多い不具合は「**要求が飛んでいない**」である。サーバ側には何も出ない。だからクライアントにも
記録者が要る:

- Vue の `app.config.errorHandler`、`window.onerror`、`unhandledrejection`。
  今この 3 つはどれも取っていない（`src/` に 1 つも無い）。
- **ペインが出した `fetch` だけ**をラップする。グローバルに包まない（下の「採らなかったもの」）。
- **B のフレームの中**は、ホストからは見えない。捕まえるにはビューに注入する bootstrap 側で
  `onerror` と `fetch` を拾う必要があり、それは core（`@mulmoclaude/core/remote-view`）と
  MulmoClaude に跨る仕事なので**後段に置く**（P5）。サーバ側の記録があるので、
  「呼ばれたか / 何を答えたか」は最初から分かる。フレーム内で拾って初めて分かるのは
  「**呼ぶ前に落ちた**」だけである。
- **C は API を呼ばない。** 記録するのはブリッジの要求・答え・拒否・無視されたモーダル呼び出しで、
  これは[プレビュー計画](./feat-shared-app-preview.md) P3 と**同じ実装**である。

## 3. 時計は 1 つしかない

サーバ側とクライアント側の突き合わせに相関 id は要らない。**同じマシンの同じ時計**なので、
時刻で正しく並ぶ。分散システムの作法をここに持ち込まないこと。

相関 id が要るのは **B だけ**である（どのフレームのどのビューが出した要求か）。それは
**既にあるビュー・トークン**が答えるので、新しい id を発明しない。

## 貼れる塊の形

読むのは人間か LLM で、渡し方はコピー & ペーストである。したがって:

- **先頭に環境** — バージョン・OS・プロジェクト・開いているコレクション / ビュー・実行文脈（A/B/C）。
  ここは `/api/diagnostics/report` と**同じ生成器**を使う（2 つ作らない）。
- **本文は時系列、1 件 1 行。** サーバ発とクライアント発は印で区別する。
- **コードフェンス 1 つ**、上限つき（目安 200 件 / 64KB）。溢れたら**古い方を落として、
  落としたと書く**。黙って切り詰めると、完全な記録に見えるのが一番悪い。
- 常に**末尾に「この記録が言えないこと」**を 1 行。ルールは評価していない、他人の端末は見ていない、
  など（プレビュー計画の表と同じ性質）。

## マスクは散文ではなくコードで

| 常に伏せる | 既定で出さない | 明示的に足せる |
|---|---|---|
| ビュー・トークン、`Authorization`、Cookie | 要求と応答の**本文** | 本文を含める（1 クリック、意味を書く） |
| ホームディレクトリの絶対パス（`~` に畳む） | クエリの**値** | — |
| 設定の allow list 外のキー（`report.ts` の規則を再利用） | レコードのフィールド**値** | — |

- **ホームパスは必ず畳む。** CLAUDE.md がスクリーンショットについて言っているのと同じ穴
  （「スクリーンショットは維持者のディレクトリを漏らす」）が、ログにもそのまま開いている。
- **フレームの中で作られた文字列は隔離する。** B と C の例外メッセージ・拒否理由は、
  **LLM が書いた HTML** が作った任意文字列である。切り詰め、出所を明記し、
  **貼る先が LLM である**ことを前提に、指示として読まれない形に囲う。
  （診断計画 3 が `window.onerror` のメッセージを本文ごと捨てた理由と同じ問題。ここでは
  読者が著者本人なので**捨てるまではしない**が、素通しもしない。）
- **ディスクに書かない。** メモリの輪バッファだけにする。書けば個人情報の置き場所が 1 つ増え、
  消す責任が生まれる。運ぶのは人間である（診断計画と同じ判断）。

## どこに出て、何を押すのか

- ペインの隅に小さな標示: 記録中・件数・**エラー件数**。エラーが 0 のときは目立たない。
- **「コピー」が主**。押した瞬間に上の塊がクリップボードに入る。
- **「隣のセルに送る」は従**。ヘッダボタンには既に「走っている agent に文字を打ち込む」型があるので、
  経路は増やさない。ただし**確認を挟む** — 外向きの操作ではないが、agent の入力を横取りするため。
- **常時記録**にする。「記録を on にしてもう一度再現してください」は往復が 1 回増えるだけである。
  MulmoTerminal はコンパイル済みの `dist/` を配っていて devtools は開いていない、という前提で
  設計すること。
- 負荷は**輪バッファの上限**で抑える。記録の配列を Vue のリアクティブにしない（200 件が
  1 件増えるたびに再描画する UI を作らない）。

## `mulmoterminal-bug-report` との関係

このスキルは今、環境の収集とマスクを**散文で**指示している（`# mask before quoting`）。
この塊ができたら、スキルは**自分でマスクする側から、受け取る側になる**。SKILL.md の該当部分は
「この塊を貼ってもらう」に置き換わる。

設定キーを足す場合（記録件数の上限など）、それは**どのスキルのものか**を先に決めること。
色でも鍵でも通知でもないので `mulmoterminal-config` の担当になる（設定は 1 つのスキルに属する）。

## 順番

| | やること | リポジトリ |
|---|---|---|
| P0 | サーバ側の輪バッファ（コレクション/ビュー系の経路だけ）＋ **200 の中の失敗**の判定を経路ごとに宣言 | MulmoTerminal |
| P1 | マスクを純関数で。MulmoClaude の `report.ts` の規則を移植（または共有）し、テストを付ける | MulmoTerminal（← MulmoClaude 参照） |
| P2 | `/api/diagnostics/*` に読み出し口。名前は MulmoClaude の名前空間に合わせる | MulmoTerminal |
| P3 | クライアント側の記録（`errorHandler` / `onerror` / `unhandledrejection` / ペイン内 `fetch`）と時系列の合成 | MulmoTerminal |
| P4 | ペインの標示と「コピー」 | MulmoTerminal |
| P5 | 「隣のセルに送る」 | MulmoTerminal |
| P6 | **B のフレーム内**の捕捉（bootstrap 側で `onerror` と `fetch`） | core / MulmoClaude と共有 |
| P7 | **C のプレビュー**の記録 = プレビュー計画 P3 と同一実装 | MulmoTerminal |

**P7 を先にやった（2026-08-15）。** 順番を変えた理由は 3 つで、A と B の順番（P0 から）は
変えていない:

- **C だけが「LLM が書いて、一度も動かしていない」コード**である。A と B は人間かプラグインが
  書いた。壊れているデバッグの往復は C のもの。
- **C はサーバ側の仕事が要らない。** `connect-src 'none'` で API を呼ばないので、P0 の輪バッファは
  C には何も足さない。全部 `SharedAppPreview.vue` の中にある。
- **記録器も語り手も既にあった。** headless preview（プレビュー計画 P5）が `channel.post` を包んで
  親の答えを記録し、観測を散文にする 16 本のテスト付きの語り手を持っている。

やったこと: 輪バッファ（`src/utils/sharedAppPreviewLog.ts`、非リアクティブ・件数だけ ref）、
**語彙を `common/sharedAppViewVocabulary.ts` に出して headless と共有**（＝ペインのコピーと
agent 自身の `action: "preview"` が同じ文を出す）、ペイン下端の件数表示と「Copy what happened」。
フレームの中の例外・無視されたモーダルは `@receptron/sharedapp` 0.6.0 の notice で届く
（[公開ビューの診断](./feat-shared-app-view-diagnostics.md) の 2 の実装でもあり、mulmoserver 側にも
そのまま効く）。

**マスクは値を入れないことで済ませた。** フィールド名とコレクション id だけを記録するので、
「本文を既定で出さない」の判断が輪バッファの型そのものになっている。ホームパスは畳む。
サインインしているアドレスは入れない（セッションの有無は、拒否された書き込みとして時系列に出る）。

P0〜P4 だけで、A と B の「何が起きたか」は運べるようになる。P6 が足すのは
「**呼ぶ前に落ちた**」の 1 種類だけで、そのために 3 リポジトリを動かす順番が要る。

## 3 つの診断計画の関係（混ぜないこと）

| | 場所 | 読者 | 何を捕まえる |
|---|---|---|---|
| この計画 | **著者のマシン**、コレクションペイン | 著者と、隣のセルの agent | ホストの API と、ペインの中の例外 |
| [プレビュー](./feat-shared-app-preview.md) | 著者のマシン、publish の**前** | 著者と LLM | 描画・配線・形（**権限は証明しない**） |
| [公開ビューの診断](./feat-shared-app-view-diagnostics.md) | **他人のブラウザ**、publish の**後** | 症状を運ぶ人間 | ルール・端末・同時実行 — 公開後にしか出ないもの |

**置き換え合わない。** ここで作る塊が便利だからといって、公開後の経路（診断計画 1〜4）を
省略できるとは考えないこと。ここに映るのは**著者のマシンで起きたことだけ**である。

## 採らなかったもの

- **`window.fetch` をグローバルに包む。** ターミナルの WS も PTY の経路も巻き込む。
  記録するのは**ペインが出したもの**に限る。
- **ディスクに書く / どこかへ送る。** 個人情報の置き場所を増やし、消す責任を生む。運ぶのは人間。
- **既定 off のトグルにする。** 「記録を on にして再現し直してください」は往復を 1 回増やすだけで、
  しかも一番知りたい**最初の 1 回**は必ず取り逃がす。
- **マスクを散文でモデルに頼む。** MulmoClaude の `report.ts` の冒頭がまさにその批判であり、
  名指しされているのはこのリポジトリのスキルである。
- **status だけで成否を判定する。** このリポジトリの API は 200 で失敗を返す。
- **本文を既定で入れる。** 貼る先は LLM で、レコードには他人の個人情報が入りうる。
- **新しい相関 id を発明する。** 時計は 1 つ、フレームの識別は既存のビュー・トークンで足りる。
- **B と C を「どちらもフレームだから」と 1 つの実装にまとめる。** 片方はホストの API を叩き、
  もう片方は `connect-src 'none'` でネットワークを持たない。記録するものが違う。

## 検査（1 行で）

> **一次資料は、ペインが自分について嘘を描いても残るもの — つまりサーバ側の記録である。**

クライアント側の記録は、それを補うためにある。順番を逆にすると、壊れたページの自己申告を
デバッグの土台にすることになる。
