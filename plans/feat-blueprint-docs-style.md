# 文書の設計図パック（1）: 規約をつくる

issue: #2301（chaff 側は isamu/lab#109）

## 何のためか

非エンジニアが「うちの文章はこう書く」を、手本の文章から取り出して残せるようにする。残す先は二つ。

- **chaff の設定（`chaff.yaml`）** — 機械が毎回確かめる決まり。ジャンル、言語、規則ごとの段階、社内用語、必須の見出し。
- **文体の手引き（`STYLE.md`）** — Claude Code が文章を書く・直すときに読む決まり。語調、文末、表記、構成など、機械では測れないもの。

この二つが、この後のパック（作る・整える・読み解く）の土台になる。

## 決めたこと

- **chaff は機械判定だけ。** 読み取りと書き起こしは Claude Code がする。パックは chaff の L4（`chaff test`、API key）を使わない。
- **検査は chaff 自身の出力で行う。** 設定が読めること（`chaff rules --json`）、手本が自分の規約で指摘されないこと（`--sarif` の件数）、わざと崩した文章には規約が効くこと。
- **規約は手本から測る。** 閾値は `chaff eval` で手本を測って決め、決めた理由を一つずつ残す。手本に無いことを規約にしない。
- **手本が自分の規約に落ちないこと**を最初の検査にする。手本で指摘が出る規約は、その文章が書けない規約である。
- **効くことも確かめる。** 手引きに反する文章をわざと書き、chaff がそれを指摘することを確かめる（コードを壊して試験が赤になるのと同じ考え方）。
- 日本語と英語の両方で動く。言語は手本から推定し、ヒアリングで上書きできる。

## パックの形

### 土台 `docs`（文書のフォルダ）

GitHub も git も要らない。文書を置くフォルダが一つあればよい。要るのは Node だけで、chaff は `npx -y chaffjs@0.6` で動かす。

| 段 | 何をする | 検査 |
| --- | --- | --- |
| `workspace` | フォルダの確認、`.blueprint/` の用意、chaff が動くことの確認 | `checks/workspace.sh` |

### 用途 `style`（規約をつくる）

ヒアリング:

- 手本（ファイル、フォルダ、URL）
- 文書の種類 → chaff のジャンル
- 言語（自動 / 日本語 / 英語）
- 誰が読むか、何のための文章か（手引きの前書きになる）
- どれくらい厳しくするか（手本に合わせる / 少し厳しく）

| 段 | 何をする | 検査 |
| --- | --- | --- |
| `sources` | 手本を `.blueprint/sources/` に集める。URL は本文だけを Markdown にする。出所を `sources.json` に残す | `checks/sources.mjs`: 数と長さ、出所の記録、読めること |
| `rules` | `chaff eval` で手本を測り、`chaff.yaml` を書く。規則ごとに段階と理由を `rule-decisions.json` に残す。`STYLE.md` を書く | `checks/rules.mjs`: 設定が読める、手本が指摘されない、決定に理由がある、手引きに必須の節がある |
| `counter` | 手引きに反する文章を `.blueprint/counter/` に書く | `checks/counter.mjs`: chaff が指摘すること、規約のうち効いた規則の数 |
| `report` | 何を規約にし、何を手引きに回し、何を規約にしなかったか | `checks/report.sh` |

## 確かめ方

- パックの定義（manifest・ヒアリング・段階）は、既存のパックと同じ試験（`test/server/blueprint/packs.spec.ts`）で読み込めることを確かめる。
- 検査のスクリプトは、正しい状態と壊した状態の両方をつくって、それぞれ成功と失敗になることを試験する（`refactorChecks.spec.ts` と同じ作り）。
- 実際にこのパックで一度規約を作ってみる。日本語と英語の手本それぞれで。
