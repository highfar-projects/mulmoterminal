# 設計図: 既存リポジトリを整えるパック（リファクタリング）

親: #2246（設計図）。新しく作るだけでなく、**既にあるリポジトリ**を、デグレと副作用なしに自動で整える。

## 目的

- コードが整う（長い関数の分解、重複の統一、到達しないコードの整理、型の境界）
- テストが整う（触る前に守りのテストを書き、壊して効くことを確かめる）
- CI が動く（lint / typecheck / test / build が PR ごとに走る）
- 判断が要るときだけ人に聞き、コミット・PR・マージまで自動で進む

## 決めたこと

- **全自動**: 一区切り（一つの領域）ごとにブランチ → コミット → push → PR → CI が緑なら `--merge` でマージ。人に聞くのは判断が要るときだけ（ベースラインが赤、証明できない移動、計画にない変更が要るなど）。PR の作成・マージを自動で行うことは、整える対象の承認（review の関門）で一度だけ同意を取る。
- **スキルの中身はパックに入れる**: 利用者の `refactor-safely` / `decompose-function` の要点を、工程ごとのスキルとして書き直して同梱する。
- **対象は TypeScript / JavaScript だけ**（最初の版）。関門は package.json の scripts。
- **始点は、利用者が clone して信頼済みのフォルダ**。Claude Code の信頼は git のルートまでしか遡らないので、clone したリポジトリは利用者自身が一度信頼する。信頼の確認に代わりに答えることはしない。
- **`.blueprint/` はコミットしない**: `.git/info/exclude` に足す（リポジトリのファイルは変えない）。

## 形

### 土台 `repo`（既存のリポジトリ）

1. `repo-check` — git リポジトリ、GitHub の origin、`gh` がログイン済み、作業ツリーが綺麗、デフォルトブランチが最新。`.blueprint/` を exclude に足す。
2. `baseline` — 使っているパッケージマネージャと関門の scripts を調べて `.blueprint/gates.json` に書き、触る前の状態で全部緑であることを確かめる。赤なら人に聞く。
3. `ci` — CI が関門を PR ごとに走らせているか。欠けていれば足す（`permissions:` 付き）。変更は PR にして CI 緑でマージ。

### 使い方 `refactor`（整える）

4. `survey` — 候補を洗い出し、コスト（「テスト可能になる規則 ÷ 書き戻すセル数」）をつけて、仕様書の場所（`.blueprint/spec.md`）に計画として書く。見送り（理由を測った no）も書く。機械が読む一覧は `.blueprint/targets.json`。
5. `tranche`【review】— 承認で計画と自動の PR・マージに同意。**残りがある限り繰り返す**（`repeatWhile`）。一回で一つの対象: 守りのテスト（未変更のコードで書き、壊して効くことを確認）→ 逐語的に移す → 同値の証明 → コードを壊して回る → 関門を終了コードで → PR → CI 緑でマージ → 対象を済みにする。
6. `report` — 証明したこと、証明できなかったこと、見送ったことと理由。

## 実行器に足すもの: 工程の繰り返し

- `planStepSchema` に `repeatWhile`（シェルのコマンド、終了コード 0 なら「まだ残りがある」）。
- 判定が通った工程に `repeatWhile` があれば、実行器がそれを走らせ、残りがあれば工程を「作業中」に戻して新しいセッションで次の回を始める。失敗回数はその回ごとに数え直す。回数には上限を置き（無限に回らない）、上限に達したら人に聞く。
- 画面には何回目かを出す。

## やらないこと（最初の版）

- TS/JS 以外の言語
- 利用者の作業中のコピーを触ること（別に clone したもので行う）
- bot レビュー（CodeRabbit など）への対応
