# 設計図（試験中）— 試してくれる人向けの案内
{: .no_toc }

「設計図」は、作りたいアプリを聞き取って仕様書にまとめ、その仕様書から工程ごとに Claude Code が組み立てていく機能です。アプリだけでなく、文書も扱えます（規約をつくる・書く・整える・読み解く・確かめる・尋ねる。[文書を扱う](#documents)）。人が決めること（仕様の確認、費用のかかる操作、公開）だけ止まって聞き、あとは最後まで自動で進みます。

> **試験中です。** MulmoTerminal 6.5.0 から入っていますが、見た目も中身も変わっていく途中です。

## 用意するもの

| | 必要なもの |
|---|---|
| 全員 | Node.js 22.13 以上、`yarn`、ログイン済みの Claude Code（`claude` が動くこと）、git |
| Firebase で試す人だけ | Google アカウント、支払い方法を登録できる Google Cloud の請求先アカウント、`firebase`（Firebase CLI）、`gcloud`、JDK 21 以上（macOS なら `brew install openjdk@21` で足ります） |
| Cloudflare で試す人だけ | Cloudflare のアカウント（無料のものでよい）。`wrangler` はプロジェクトに入るので、別に入れる必要はありません |
| Supabase で試す人だけ | Docker Desktop（起動しておく）、Supabase のアカウントと Cloudflare のアカウント（どちらも無料のものでよい）。Supabase の CLI と `wrangler` はプロジェクトに入ります |

まずはローカル（Firebase なし）で試してください。こちらは自分の PC の中だけで完結し、費用もクラウドの設定も要りません。

> **Claude の利用量について**: 1 回のビルドは工程ごとに Claude Code のセッションを起こすので、ふつうにチャットするよりまとまった量を使います。

## 動かす

```bash
npx mulmoterminal@latest
```

ブラウザで `http://localhost:34567` を開きます。上のバーの「その他の機能」メニュー（`widgets` アイコン）に「設計図」があれば準備完了です（`npx mulmoterminal --version` が 6.5.0 以上であること）。

- 設計図を動かせるのは、**1 台の PC で 1 つの MulmoTerminal だけ**です。MulmoTerminal を 2 つ同時に起こすと、あとから起こした方は一覧を見ることはできても、操作すると「このマシンの設計図は、ポート … の MulmoTerminal が動かしています」と断られます。
- 各工程のエージェントは、いつものグリッドには出てきません。何をしているかは設計図の画面に表示されます。

## 作業用フォルダを信頼しておく {#trust}

エージェントは誰も見ていないところで動くので、Claude Code の「このフォルダを信頼しますか？」で止まると先へ進めません。そのため、**信頼済みのフォルダの中**でしか始められないようになっています。一度だけ次の準備をしてください。

1. 試し用の親フォルダを作ります（例: `mkdir ~/blueprint-trials`）。
2. そのフォルダで `claude` を起動し、信頼するかを聞かれたら「はい」を選んで、すぐ終了します。
3. 以後は、ビルドのたびにこの中のフォルダを使います。まだ無いフォルダ名（例: `~/blueprint-trials/library`）を入れれば、「始める」を押したときに作られます。新しいフォルダは親の信頼を引き継ぐので、改めて信頼する必要はありません。`~` はホームフォルダのことで、欄にそのまま入れて構いません（Windows なら `~\blueprint-trials\library` でも `C:\Users\<名前>\blueprint-trials\library` でも同じです）。

準備をせずに「始める」を押して信頼していないと断られたときは、その下の「ここで Claude Code を開く」を押します。信頼の確認に答えるべきフォルダ（そのフォルダ、まだ無いフォルダならその親）で Claude Code が新しいターミナルに開き、信頼するかを聞かれるので、自分で答えます。設計図に戻ると入れていた内容が戻っているので、もう一度「始める」を押すだけです。工程の途中で同じ理由で止まったとき（工程がフォルダを git のリポジトリにしたときなど）も、実行画面に同じボタンが出ます。答えたら、そのビルドを選んで「もう一度」を押します。

> **作ったフォルダで `git init` はしないでください**。git のリポジトリになったフォルダは親の信頼を引き継がなくなり、途中の工程で止まります。git で管理したいときは、ビルドが終わってからにしてください。

## 最初の一回: 「おうち図書館」

家にある本と、誰に貸しているかを記録する小さなアプリを、自分の PC の中に作ります。

1. 「その他の機能」→「設計図」→「新しく作る」を開きます。
2. 「例から始める」で **おうち図書館** の「この例で始める」を押します。土台（ローカル）、作るものの種類（自由に作る）と質問への答えが入ります。
3. 「プロジェクトのフォルダ」には、最近のビルドの隣など信頼済みの場所に、この例のための新しいフォルダが入ります。入らなかったとき（初めてのときなど）は `~/blueprint-trials/library` のように入れます。そのまま「始める」を押すと、フォルダが作られて始まります。
4. 最初の工程で仕様書ができると、**仕様書の画面**で止まります。ここがいちばん大事なところです。
   - 仕様書を読み、「決めていないこと」が残っていれば確認します。
   - 変えたいことがあれば、下の欄に書いて送ります（例: 「本の削除もできるようにして」）。エージェントが仕様書を直して返事をします。
   - 納得したら「承認する」を押します。
5. あとは工程が順に進みます。作業中の工程では、エージェントが何をしているかと経過時間が表示されます。左の一覧では、承認や答えを待っているビルドと止まったビルドが、いちばん上の「あなたを待っている」にまとまります。もう見なくてよいビルドは、画面上の「一覧からしまう」で一覧のいちばん下の閉じた「しまったビルド」に移せます。何も消えず、「一覧に戻す」でいつでも戻せます。
   - 「質問が届いています」と出たら、答えを書いて「送る」を押します。
   - 工程が止まったら、「判定の結果」を読んで「もう一度」を押せます。
   - 最後の手前に「セキュリティ診断」の工程があります。OWASP Top 10:2025 の観点で作ったものを読み、突ける穴を直して試験を足し、`.blueprint/security-review.md` に報告を書きます。判定は、起動したアプリに攻撃と同じ形のリクエスト（別の名前の `Host` による DNS リバインディング、別のサイトからの変更、壊れた JSON）を送り、断ることを確かめます。依存の脆弱性（`yarn audit`）も見ます。Firebase では本番に公開する前にこの工程が入り、直したものを開発用に公開し直して、画面が壊れていないことまで確かめます。
6. 「すべての工程が完了しました」と出たら終わりです。そのすぐ下に**使い始め方**（`.blueprint/start-here.md`）が出ます。起動のしかた（`yarn start`）と開くアドレス、必須の機能を一つずつ試すチェックリスト、データの置き場所が書かれているので、上から順に試してください。詳しいことはフォルダの `README.md` にあります。Firebase では、本番の URL と、次に直すときの手順（開発用で試してから本番へ）が出ます。

## 試してほしいこと

できた範囲で構いません。どれを試したかも教えてください。

**基本の流れ**
- [ ] おうち図書館を最後まで作り、できたアプリが動く
- [ ] 仕様書の画面で会話をして、仕様書が直る（何往復かしてみる）
- [ ] ほかの例（家計簿・チームのタスクボード・見積書づくり）を一つ作る
- [ ] 例を使わず「自由に作る」で、自分の作りたいものを一つ作る

**止まり方・戻り方**
- [ ] 質問に答えると先へ進む
- [ ] 承認のところで「やめる」を押すと、そこで止まる
- [ ] 作業中に MulmoTerminal を止めて起こし直すと、その工程をやり直して続く
- [ ] 画面の案内（質問の手順）だけで、迷わず操作できる

### コレクションからアプリにする {#from-collection}

MulmoTerminal のコレクションを元に、自分のコードとして持つアプリを作ります。土台はローカル・Firebase・Cloudflare・Supabase から選べます。手順の全体は専用のページ [コレクションからアプリにする](from-collection.html) にまとめています。「作るものの種類」で **コレクションからアプリにする** を選び、「元にするコレクション」でワークスペースのコレクションを一つ選びます。

- 「始める」を押すと、選んだコレクションと、`ref` などでつながっているコレクションの形（`schema.json`、`SKILL.md`、宣言されたビューとテンプレート）が、作るフォルダの `.blueprint/source/` に写されます。元のコレクションは変わりません。
- 「記録（中のデータ）も写しますか」で **はい** を選ぶと、記録と、記録が指す画像・ファイルも写し、「記録を移す」の工程でアプリのデータベースと `data/files/` に移します。移した結果は、仕様どおりの表に全件・全項目が元の値のまま入っているかを機械で突き合わせて確かめます。記録に個人情報があれば、それも新しいフォルダに写ります。個人情報になり得る項目（メールの項目や、名前・電話・住所などを表す項目）がある元では、「始める」を押すと一度だけ止まり、その項目を並べて見せます。確かめて「確かめたので、写して始める」を押すと始まります。共有アプリでは、メンバーのメールアドレスが `app.json` と一緒に写るので、記録を写さなくても同じ確認が出ます。**いいえ** なら形だけを写し、空のアプリができます。
- Firebase の土台では、記録を Firestore に、画像・ファイルを Cloud Storage に移します。まずエミュレータで移して確かめ、本番へは「本番に公開」のあと、もう一度承認してから移します。本番では、あなたの Google アカウント（`gcloud auth application-default login`）で書き込み、移したあと本番を読み直して元と突き合わせます。
- Cloudflare の土台では、記録を D1 に、画像・ファイルを R2 に移します。まず手元（`wrangler` のローカルの状態）に移して確かめ、`yarn start` で開くアプリにも記録が入ります。本番へは「Cloudflare に公開」のあと、もう一度承認してから `yarn import-source --remote` で移し、`wrangler` で本番を読み直して元と突き合わせます。書き込みは、あなたが `yarn wrangler login` でログインしたアカウントで行います。
- Supabase の土台では、記録を Postgres に、画像・ファイルを Storage に移します。まず手元の Supabase 一式に移して確かめ、`yarn start` で開くアプリにも記録が入ります。移した記録の持ち主は、既定ではあなた自身のアカウントです（手元では試しのデータの利用者）。本番へは「Supabase と Cloudflare に公開」のあと、もう一度承認してから、公開したアプリに登録したメールアドレスを添えて `yarn import-source --linked --owner <メール>` で移します。移したあと、Supabase の CLI で本番を読み直して元と突き合わせます。書き込みは `yarn supabase login` と `link` をした、あなたのアカウントで行います（秘密の鍵は使いません）。
- 写す量には上限（200 MB）があります。超えると始める前に断られるので、記録を写さずに始めてください。
- 仕様書の画面では、元の項目・ビュー・アクション・自動取り込みが、どのコレクションのものかが分かる名前（`books.title` のような形）で並びます。一つでも欠けると、仕様書の工程は先へ進みません。アクション（エージェントに頼む操作）と自動取り込みは、それぞれ「機能にする」「人が手で行う」「やめる」のどれにするかが提案として並びます。承認の前に、仕様書の会話で決め直せます。「機能にする」ものは「アクションを機能にする」の工程で作られます。AI が要る手順は、サーバーから Claude API を呼ぶ機能になり、鍵は `.env`（Firebase ではシークレット、Cloudflare では手元は `.dev.vars`・本番は `wrangler secret put`、Supabase では Edge Functions の `supabase/functions/.env`・本番は `supabase secrets set`）に置きます。「人が手で行う」ものは README に手順が書かれます。
- **共有アプリ**も元に選べます。ワークスペースと保存したフォルダのうち `app.json` を持つものが、「元にするコレクション」の欄の「共有アプリ」の下に出ます。選ぶとアプリ全体（`app.json` と全コレクションの形）を写し、仕様書では、メンバーと役割・公開の申込み・見える範囲・メールといった宣言を「誰が何をできるか」に写します（`app.members` や `app.public.submit.<コレクション>` のような名前で、一つ残らず書かれているかを機械で確かめます）。記録も写すときは、あなたのサインインで Firestore から読みます。先に共有アプリへ接続しておくこと、そして全件を読める役割（owner・editor・viewer）であることが要ります。そうでなければ、始める前に理由を示して断ります。
- 写しは始めたときに一度だけ取ります。その後に元（コレクションや共有アプリ）が変わると、その作業を開いたときに「写しを取った後に変わっています」と一行出ます。作業はその写しのまま進むので、新しい内容を使うなら同じ元から新しく作り直してください。

### 文書を扱う {#documents}

「作るものの種類」で文書の仕事（一覧の「文書のフォルダ」の下にあるもの）を選ぶと、アプリの代わりに文書を扱います。文書の仕事は「文書のフォルダ」でしか動かないので、土台を選ぶ欄は出ません（土台を選ぶ欄は、いくつかの土台から選べるアプリのときだけ出ます）。文章の検査には chaff を使います（自動で取ってくるので準備は要りません）。文書を入れたフォルダを信頼済みの親フォルダの中に作り、「作るものの種類」で次のどれかを選びます。

| 作るものの種類 | すること |
|---|---|
| 規約をつくる（手本の文章から） | 手本の文章から「うちの文章はこう書く」を取り出し、機械が確かめる決まり（`chaff.yaml`）と書くときの手引き（`STYLE.md`）にする |
| 文書を書く（規約に沿って） | 頼んだ文書を、フォルダの規約に沿って一部分ずつ書く |
| 文書を整える（書いてあることは変えずに） | 今ある文書を、中身は変えずに読みやすくする。原本は残る。文書の種類（報告書・ブログなど）を選ぶと、その種類で大事なところ（結論が先か、頼みごとに期限があるか、など）も読み、書き足しが要るところは直さずに書いた人への質問にする |
| 文書を読み解く（矛盾と不備を見つけて直し方を出す） | 契約書や規程の食い違いや抜けを見つけ、直し方を別のファイルに出す |
| 文書を確かめる（日付・曜日・順番・合計を機械で） | 旅程表や見積書の日付・曜日・順番・合計の誤りを機械で見つける |
| 要約する（一文ごとに原文で裏付けて） | 長い文書を決めた長さに要約する。一文ごとに原文の引用を付け、どの部分も黙って落とさず、数字は引用のとおりかを機械で確かめる |
| 用語をそろえる（用語集をつくって chaff に入れる） | 文書から定義された語、二重定義、表記ゆれを集めて用語集にする。望めば使う書き方をフォルダの chaff.yaml に入れ、以後は chaff が揺れを指摘する |
| 文書のフォルダに chaff を入れる（今ある指摘は棚に上げて） | 既にある文書に、種類に合わせた chaff.yaml を置き、今ある指摘は棚に上げて、新しい指摘だけが出るようにする。望めば GitHub の PR の行に指摘が出るワークフローも作る |
| 版を比べる（新旧対照表をつくる） | 契約書や規程の旧版と新版を条ごとに対応づけ、変わった・足された・消えた条を新旧対照表にする。変わったかどうかは本文を機械で比べて決める |
| 文書に尋ねる（どこに書いてあるかを添えて） | 文書に質問し、どこに書いてあるかを添えた答えをもらう |

「プロジェクトのフォルダ」の欄を押すと、これまでのビルドのフォルダと、MulmoTerminal に保存してあるフォルダが候補に出るので、選べます（打ち込んでも構いません）。自分の文書を扱うときは、質問の「読み解く文書」「整えたい文書」などの下にある「フォルダから選ぶ」を押すと、そのフォルダの中のファイルが並ぶので、押して選べます（一行に一つ。手で打ち込んでも構いません）。

途中で「承認が必要です」と止まったら、「承認する前に読むもの」に並んだファイル（見つけたこと、要旨、構成など）を押して開き、確かめてから「承認する」を押します。

手元に文書が無くても試せます。「例から始める」の「文書のフォルダ」の見出しの下に文書の例（業務委託契約書を読み解く、旅程表を確かめる、業務委託契約書の改定を比べる、経費精算の手引きに尋ねる、経費精算の手引きを要約する、テレワークの規程と手引きの用語をそろえる、ヘルプのページに chaff を入れる、社内のお知らせを整える、報告書を報告書として整える、ブログ記事をブログとして整える、社内の手続きの文章から規約をつくる、新しく入った人向けの手引きを書く）があり、選ぶと新しいフォルダが入るので、そのまま始めると、見本の文書がそのフォルダに置かれます。既にあるフォルダを選んだ場合、同じ名前の別のファイルがあると始まりません。終わると、設計図の画面に報告（見つけたこと・確かめたこと・残したこと）がそのまま表示されます。作業で変わったファイルの一覧も出て、押すとそのファイルが開きます。

規約をつくったフォルダでは、終わった画面の「次にできること」から「文書を書く」「文書を整える」へ進めます。押すと、同じフォルダと「このフォルダの規約」を入れた状態で新しく作る画面が開くので、質問を確かめて「始める」を押します。書き終えたあとは「文書を整える」へ進めます。このときは、書いた文書、同じ規約、「手引き（STYLE.md）の決まりにも合わせる」が入ります。書くあいだに chaff で部分ごとに確かめてあるので、残っているのは手引きと読み比べて整えることだからです。

- [ ] 「文書を確かめる」: 旅程表や見積書を入れると、曜日の誤り、予定の順番の入れ違いや時間の重なり、合計が内訳の和になっていないところを、機械が見つけて報告する。わざと曜日や合計を間違えた旅程で、その誤りが報告に出る
- [ ] 「文書を読み解く」: 契約書や規程の、存在しない条への参照や食い違いが、原文の引用付きで出る。chaff が間違えた所（読み解いて退けた指摘、chaff が見逃した構造の問題）は、chaff への報告の下書きとして `.blueprint/chaff-feedback/` に残る。下書きは何も送らないので、読んでから送るかを決める
- [ ] 「文書に尋ねる」: 質問に、文書のどこに書いてあるかを添えて答える

**Cloudflare**

Cloudflare の土台は、Worker（API）と D1（SQLite のデータ）と、同じ Worker が配る Vue の画面でできたアプリを作ります。途中までは `wrangler dev` で自分の PC の中だけで動かして確かめ、「Cloudflare に公開」の工程で初めて、承認してから公開します。公開のときは `yarn wrangler login` を自分で実行して、Cloudflare にログインします（設計図は API トークンを扱いません）。公開したアプリは URL を知っている誰でも開けるので、ログインの方式と、ログインしない人に見せてよいものを、仕様書の段階で必ず決めてください。

- [ ] 「自由に作る」を土台 Cloudflare で作り、手元の `yarn start` で動き、公開した URL でも同じように動く
- [ ] 「使い始め方」に公開した URL と、試すことのチェックリストが出る

**Supabase**

Supabase の土台は、データ・ログイン・権限を Supabase（Postgres）に置き、Vue の画面を Cloudflare から配るアプリを作ります。画面はブラウザから Supabase を直接読み書きするので、誰が何を読み書きできるかは、表ごとの行ごとの権限（RLS）で決めます。仕様書には、表ごとに「読める人・足せる人・変えられる人・消せる人」を書きます。途中までは Docker の中の Supabase 一式（`yarn start` が起動します）で、自分の PC の中だけで動かして確かめます。セキュリティ診断では、Supabase の診断に加えて、ログインしていない人と、何も持っていないログインした人として全部の表を読み書きしてみて、仕様で許したこと以外が通らないことを確かめます。公開は「Supabase と Cloudflare に公開」の工程で、承認してから行います。Supabase のプロジェクトは自分で作り（無料のプランで足ります）、`yarn supabase login` と `yarn supabase link` と `yarn wrangler login` を自分で実行します（設計図はパスワードやトークンを扱いません）。

- [ ] 「自由に作る」を土台 Supabase で作り、手元の `yarn start` でログインして使え、別のアカウントからは最初のアカウントのデータが見えない
- [ ] 公開した URL でも同じように動き、「使い始め方」に公開した URL と、試すことのチェックリストが出る

**Firebase（慣れている人だけ）**

Firebase の土台は、開発用とそれとは別の本番用、2 つの Firebase プロジェクトを使い、従量課金（Blaze）への切り替えも必要です。いまのところ確かめているのは**開発用への公開まで**です。本番への公開の承認はしないでください。

- [ ] 「ミニ SNS」の例で、開発用に公開されたアプリに Google でログインできる
- [ ] 土台 Firebase・種類「社内向け業務アプリ」の「稟議」の例で、会社のドメイン以外のアカウントが断られ、その画面がわかりやすい
- [ ] コンソールでの操作を頼まれたとき、質問に書かれた手順だけでできる

## 困ったとき

| 起きたこと | 見るところ |
|---|---|
| 「始める」で「Claude Code がまだ … を信頼していません」と断られる | その下の「ここで Claude Code を開く」を押して、信頼の確認に答えます（[作業用フォルダを信頼しておく](#trust)）。フォルダが git のリポジトリになっていないかも確認 |
| 「… がありません。新しいフォルダは、既にあるフォルダの中にだけ作れます」と断られる | 作るのは最後の一段だけです。途中のフォルダ（親）を先に作るか、既にあるフォルダの中を指定します |
| 工程が止まった | 「判定の結果」に理由が出ます。「もう一度」でやり直せます |
| 操作すると「このマシンの設計図は、ポート … の MulmoTerminal が動かしています」と断られる | この PC で MulmoTerminal がほかにも動いています。そちらを使うか、止めてください |
| ビルドの記録を消したい | `~/.mulmoterminal/blueprints/runs/` の中の、そのビルドのフォルダを消します。作ったアプリのフォルダはそのまま残ります |

## 報告のしかた

うまくいったことも、いかなかったことも [issue #2246](https://github.com/receptron/mulmoterminal/issues/2246) にコメントしてください。次があると助かります。

- MulmoTerminal のバージョン（`npx mulmoterminal --version` の結果）
- 土台・作るものの種類・使った例（自分で書いたなら、その内容のあらまし）
- 何をしたら、何が起きたか。期待していたことは何か
- 画面のスクリーンショット（ビルドの画面の URL `http://localhost:34567/blueprints/…` も）
- 止まった工程の「判定の結果」の文言

> スクリーンショットや文言に、メールアドレス・プロジェクト ID・フォルダのパスなど見せたくないものが写っていたら、隠してから貼ってください。

## わかっている制限

- Firebase の本番への公開（`protect` 以降の工程）は、まだ実際には確かめていません。
- コンソールでの操作の手順は、Firebase のコンソールの表示が変わると合わなくなることがあります。合わなかったら、どの画面で何が違ったかを教えてください。
- 公開後の確認は「画面が真っ白でないこと」までで、読み込み中のまま止まる不具合は見逃すことがあります。
- 「マーケット」（外からパックを取り込む画面）は試作です。公式の一覧はまだありません。
- 設計図の画面の文字（ボタン・状態・断りの文など）は、MulmoTerminal の表示言語に合わせて出ます（日本語・英語・韓国語・中国語の簡体字と繁体字）。ただし、同梱のパックの中身（作るものの種類の名前、質問、工程の名前、例）は日本語だけです。文書そのものは英語でも扱えます（「規約をつくる」で言語に「英語」を選べ、chaff は英語の文も確かめます）。
